## 第 13 章：三原生交响曲 —— 运筹优化（OR）与机器学习（ML）的三大双向增强

在许多企业的数字化建设中，运筹优化团队与机器学习团队往往处于各自为战的割裂状态：机器学习工程师在外部数据平台上训练预测模型，通过接口向业务系统吐出一个孤立的预测数字；运筹算法工程师则将这个数字直接当作确定性常数塞进线性规划模型里求解。一旦排产结果在现场执行拉胯，两边就会陷入无休止的扯皮——运筹团队怪预测不准，机器学习团队怪排产模型太脆弱。

在“三原生统一于形式化领域模型”的架构下，运筹优化与机器学习的交叉**绝不是让统计模型去替代运筹求解器，也不是把严谨的业务硬约束粗暴地改写成神经网络的奖励函数（Reward Function），而是让“统计/概率解释”与“符号/优化解释”在形式化领域契约下实现双向赋能**。

### 13.1 机器学习原生（ML-Native）：冻结特征模式与数据版本，让产能与耗时预测携带质量指标、不确定性与血缘进入审批流

要让机器学习与运筹优化安全协同，第一步必须先将外部黑盒预测改造为平台可治理的一等公民——即实现**机器学习原生（ML-Native）**。

所谓“机器学习原生”，其核心含义不是“业务系统能够通过 HTTP 接口调用一个模型服务”，而是**由形式化领域模型统一定义稳定的特征、标签、预测目标、决策反馈、可校准参数、物理单位、时间口径与结果语义，并使训练数据集、特征模式定义（Feature Schema）、模型制品（Model Artifact）以及在线推理的输入输出全部实现不可变版本化、可校验与可历史回放**。

让我们回到第 4 章与第 5 章的贯穿用例——**工厂日历（Calendar）与产线 A、B 的有效产能估算场景**，看一看一个符合“机器学习原生”标准的预测闭环是如何运转的：

```text
┌────────────────────────┐    ┌────────────────────────┐    ┌────────────────────────┐    ┌────────────────────────┐
│ 1. 领域观察事实归一化  │    │ 2. 训练与推理版本冻结  │    │ 3. 结构化预测快照输出  │    │ 4. 准入校验与审批激活  │
│ 明确工作单元/合格产量/ │───>│ 冻结特征Schema/观察窗口│───>│ 输出估算值+质量指标+   │───>│ 校验单位/阈值/新鲜度后 │
│ 实际耗时/单位/事件时间 │    │ /标签截止点/模型制品哈希│    │ 置信区间/不确定性+血缘 │    │ 激活为有效产能覆盖层   │
└────────────────────────┘    └────────────────────────┘    └────────────────────────┘    └────────────────────────┘
```

1. **生产执行观察的领域归一化**：当 MES 上报已完工任务的执行记录时，系统首先按照领域层规则将其归一化为标准生产观察事实，显式明确工作单元（Work Unit）、合格产量、实际生产耗时、目标物理单位、业务事件发生时间（Event Time）以及历史观察窗口，绝不允许机器学习脚本自行猜测或临时拼凑业务口径。
2. **输入与模型制品的不可变冻结**：在发起训练或在线推理时，应用层强制冻结本次计算所使用的特征模式定义（Schema）、观察窗口范围、标签成熟截止时点（防止将未来数据混入特征造成数据泄漏）、模型制品版本、运行配置以及输入内容哈希（Content Hash）；机器学习运行时只允许消费已冻结的确定性输入。
3. **带不确定性与血缘的结构化输出**：模型推理产出的**绝不是“真实产能事实”**，而是一份结构化的产能估算结果（如 `estimatedProductivity[A]`），其中必须完整携带模型版本号、评估质量指标、置信区间或概率分布（不确定性）、业务适用范围、血缘追踪信息（Provenance）以及失败时的结构化错误码。
4. **应用层准入校验、人工审批与覆盖层激活**：产能估算结果首先以不可变快照的形式保存样本证据；随后由应用层执行严格的物理单位检查、有限值检查（拒绝 `NaN` 或无穷大）、数据新鲜度检查、质量阈值检查与适用范围校验。只有通过校验并经业务审批与激活后，该估算结果才能正式转化为**有效产能覆盖层（`CapacityEffectiveOverlay`）**，冻结进入主生产计划（MPS）与详细排产的输入快照中，绝不能绕过审批直接冒充人工配置或实际产能事实。

在工程演进上，这套机制具有极佳的平滑演进性：例如在平台建设初期，日历产能估算可以先内置算术平均（Arithmetic Mean）与指数时间加权平均（EWMA）等确定性统计估算器，先把“观察归一化 → 样本证据 → 不可变快照 → 审批激活 → MPS 输入冻结”的业务治理闭环跑通；待后续接入复杂的深度学习或树模型时，只需在受控运行时中替换模型制品即可无缝复用整套领域语义与准入链路，历史推理也始终严格按当时冻结的模型版本精确回放，绝不回退到当前最新模型。

### 13.2 增强机制一（ML 辅助 OR）：从单点预测走向鲁棒优化、随机规划、机会约束、CVaR 与分布鲁棒优化（DRO）

当机器学习原生解决了预测结果的可信准入与不确定性量化后，它与运筹原生的第一种协同模式——**机器学习辅助运筹优化（ML-Assisted OR）**便水到渠成。

在传统排产中，即使引入了预测模型，往往也只是取一个“单点期望值”（例如预测产线 A 明天生产率为 `100 kg/h`）代入确定性运筹模型。然而工业现场充满了随机波动：设备可能出现微停机、不同批次原料的加工难度不同、WMS 备料与 TMS 在途时间也存在波动。如果只按单点平均值排满产能，计划在现实中几乎必然因为局部波动而发生连环延误。

通过“机器学习描述数据驱动的不确定性 + 运筹优化生成满足约束的风险感知决策”，我们可以将单点排产升级为五种高阶风险感知优化范式：

| 风险感知优化范式 | 机器学习原生（ML-Native）提供的输入结构 | 运筹原生（OR-Native）编译生成的数学模型 | 解决的工业与供应链核心痛点 |
| :--- | :--- | :--- | :--- |
| **1. 鲁棒优化**<br>（Robust Optimization, RO） | 基于历史残差与特征学习出的可解释、可版本化的**有界不确定集（Uncertainty Set）**及相关性边界。 | 编译为鲁棒对偶等价约束或切平面模型，确保方案在给定扰动集合的所有最坏情况下依然严格可行。 | 保障核心瓶颈产线或共享投料口在加工时长与产能波动范围内绝不发生物理超限或违约。 |
| **2. 随机规划**<br>（Stochastic Programming, SP） | 基于历史分布采样或生成模型产出的**带显式概率权重的离散场景集（Scenario Tree / Set）**（如高/中/低产能与需求场景）。 | 构建两阶段或多阶段随机规划（常配合第 11 章的 Benders 分解求解），优化跨场景的期望总成本与服务水平。 | 在需求、产能或到料交期存在多种可能走势时，找到兼顾基准成本与调整弹性的主计划。 |
| **3. 机会约束规划**<br>（Chance Constraints） | 预测关键随机变量（如工序完工耗时、在途运输时长）的参数化概率分布或分位数函数。 | 将“硬约束 100% 成立”转化为“约束成立的概率不低于置信水平 $1 - \alpha$（如 95%）”的确定性等价约束。 | 显式控制订单延期、产线缺料或超产能等风险事件的发生概率上限。 |
| **4. 条件风险价值**<br>（CVaR 优化） | 预测损失分布的尾部特征与极端场景样本。 | 在目标函数或约束中引入 CVaR 辅助变量与线性化片段，直接约束最差 $\alpha\%$ 极端情况下的平均损失。 | 不仅关注平均准时率，更重点防范极端延误或大额违约金等“黑天鹅”尾部风险。 |
| **5. 分布鲁棒优化**<br>（DRO） | 在历史样本有限或存在轻微分布漂移时，提供以经验分布为中心、以 Wasserstein 距离或矩信息为半径的**模糊集（Ambiguity Set）**。 | 编译为分布鲁棒优化模型，对模糊集内的一整族可能概率分布（而非单一经验分布）保持稳健最优。 | 解决新产线投产初期、新产品导入期历史样本稀缺导致的单点分布过拟合风险。 |

在工程治理上，每一轮风险感知排产都必须**同时冻结预测模型版本、特征模式定义、训练/推理输入快照、场景集或不确定集生成规则、风险厌恶参数以及运筹优化模型版本**。一旦检测到机器学习输出的质量指标不达标、数据已过期或当前工况越出了模型的声明适用范围，应用层必须立即拦截拒绝，自动**降级为经业务批准的静态基准不确定集**或转交人工确认，绝对禁止在后台静默使用未经验收的当前模型去重建历史场景。

### 13.3 增强机制二（OR 约束下的 ML/RL）：用受约束强化学习加速列生成定价与 Benders 子问题，由运筹主问题守住可行性与精确兜底

在许多热门的 AI 论文中，常有人尝试用端到端的强化学习（Reinforcement Learning, RL）直接替代运筹求解器来输出排产动作。然而在严肃的工业现场，这种“让 RL 直接下发排产指令”的做法极难落地：因为神经网络策略无法保证 100% 满足成千上万条复杂的物理硬约束（如共享投料口上限、物料守恒、工序先后序），也无法提供当前解距离理论最优解还有多远的数学上下界证明。

因此，本书架构确立了第二种协同范式——**运筹优化约束下的机器学习/强化学习（Constrained ML/RL under OR Master Problem）**。

我们的核心架构原则是：**绝不让强化学习直接面向业务状态下发生产动作，而是将强化学习作为第 11 章大规模分解算法（列生成与 Benders 分解）内部受严格约束的“学习型子问题加速器”**！运筹优化始终牢牢掌控主问题、硬约束边界、候选验证、上下界计算与最终收敛判定。

```text
                【形式化领域模型 + 冻结的排产求解快照】
                                   │
                                   ▼
     ┌───────────────────────────────────────────────────────────┐
     │ 1. 运筹优化构建受限主问题（RMP） / Benders 分解主问题      │
     │ • 掌控全局硬约束、当前上下界（Bounds）与收敛终止标准      │
     └─────────────────────────────┬─────────────────────────────┘
                                   │ 下发带主问题状态、对偶信息与业务边界的子问题契约
                                   ▼
     ┌───────────────────────────────────────────────────────────┐
     │ 2. 机器学习 / 强化学习（ML / RL 学习型子问题加速器）      │
     │ • 快速生成或排序候选列、候选割、候选子问题解或热启动提示  │
     └─────────────────────────────┬─────────────────────────────┘
                                   │ 提交内部候选
                                   ▼
     ┌───────────────────────────────────────────────────────────┐
     │ 3. 运筹优化确定性验证守卫（OR Verification Guard）        │
     │ • 严格检验领域硬约束可行性、约化成本（Reduced Cost）      │
     │   以及 Benders 割平面的数学有效性与上下界                 │
     └──────────────┬─────────────────────────────┬──────────────┘
           【验证通过】                 【验证失败 或 候选改进不足】
                    │                             │
                    ▼                             ▼
     ┌──────────────────────────┐  ┌─────────────────────────────┐
     │ 回注主问题并继续快速迭代 │  │ 4. 精确子问题或确定性启发式 │
     └──────────────┬───────────┘  │    强制兜底（Exact Fallback）│
                    │              └──────────────┬──────────────┘
                    └──────────────┬──────────────┘
                                   ▼
     ┌───────────────────────────────────────────────────────────┐
     │ 5. 运筹优化根据经认证的上下界与终止条件判定最终收敛       │
     └───────────────────────────────────────────────────────────┘
```

如上图所示，这套“OR 主控 + RL 加速 + 精确兜底”的协同链路严格死守五条工程边界：

1. **在列生成 / 分支定价（Branch-and-Price）中的边界**：强化学习可以根据当前主问题的对偶价格与资源状态，快速生成或排序高价值候选列、选择定价启发式策略，或为定价子问题提供高质量的热启动（Warm Start）。但**每一个由 RL 产出的候选列在进入受限主问题前，必须通过运筹层的业务硬约束可行性校验与约化成本（Reduced Cost）独立核验**。更重要的是，当算法接近收敛或需要给出最优性证明时，系统**必须强制运行可认证的精确定价子问题**，严格证明已不存在满足分支约束的改进列。
2. **在 Benders 分解中的边界**：强化学习可以用来动态选择子问题的求解策略、优化多随机场景的求解顺序、管理割平面池（Cut Pool）的优先级，或者直接预测提出候选割（Candidate Cuts）。但**任何可行割（Feasibility Cut）与最优割（Optimality Cut）都必须由运筹优化层根据经过认证的原始/对偶信息验证其数学有效性**；主问题的上下界与终止间隙绝不能由 RL 的价值网络估计值替代。
3. **策略制品与奖励函数治理边界**：强化学习的状态空间、动作空间、奖励函数定义、训练数据集、策略模型制品（Policy Artifact）与适用范围必须像普通 ML 模型一样严格版本化。奖励函数只用于引导求解搜索效率或提升候选生成质量，**绝不能成为业务硬约束的唯一来源**。
4. **100% 可复现与自动降级兜底边界**：每一轮调用 RL 加速的排产求解，都必须完整记录所用的策略版本、随机数种子（Random Seed）、生成的候选列表、被运筹守卫拒绝的原因、触发精确子问题兜底的时机以及最终收敛认证依据。一旦检测到 RL 策略发生分布漂移、推理超时或产出的候选均为不可行/非改进列，求解管线必须能毫秒级无缝退回确定性启发式或精确子问题求解，确保系统在完全禁用 RL 时依然能独立完成求解与认证。
5. **业务状态写入隔离边界**：强化学习的全部输出仅仅是运筹优化求解器内部的瞬态候选或求解提示（Hints），最终仍须经由运筹优化的结构化解解析与应用层校验，才能转换为正式领域方案；强化学习组件绝无权限直接修改领域聚合状态或触发生产下发副作用。

### 13.4 增强机制三（决策反馈驱动的参数校准）：从计划员的人工调整差异与原因码中学习目标权重与软约束偏好

运筹原生与机器学习原生的第三种深度协同，直指工业软件落地中最普遍的一个痛点：**为什么运筹算法算出来的“数学最优计划”，计划员拿到手后总是要手工改上好几处才肯下发？**

原因在于，真实的生产运营中存在着大量“只可意会、难以一次性由实施顾问精准给出定量数字”的权衡偏好——比如在特定旺季，相比于多换产两次（换产成本），车间其实更看重不让某几家核心客户延期哪怕半小时（交期权重）；或者在某条老旧产线上，计划员宁可留出 10% 的安全产能缓冲（软约束罚系数），也不愿把设备排到极限。

当运筹优化给出的原始方案经过计划员手工调整后，**原始方案与人工修改方案之间的结构化差异（Diff），实际上蕴含着宝贵的领域知识——它揭示了当前数学模型的目标函数权重或软约束罚系数尚未完整表达的稳定业务偏好**！

为此，我们构建了第三条增强闭环——**决策反馈驱动的运筹优化参数校准（Decision-Feedback-Driven OR Parameter Calibration）**。系统利用逆向优化（Inverse Optimization）、偏好学习（Preference Learning）或排序学习（Learning to Rank）等受控参数学习方法，从历史决策反馈中持续校准那些**已被领域层显式声明为“允许学习（Learnable）”的运筹参数**：

```text
┌────────────────────────────┐    ┌────────────────────────────┐    ┌────────────────────────────┐
│ 1. 冻结输入与运筹原始求解  │    │ 2. 捕获人工微调与原因分类  │    │ 3. 受控训练可校准参数候选  │
│ 基于冻结输入与当前参数版本 │───>│ 记录方案Diff、结构化原因码 │───>│ 仅针对稳定偏好样本，学习目 │
│ 产出运筹优化原始基准方案   │    │ 、审批链与后续真实执行结果 │    │ 标权重与软约束罚系数候选值 │
└────────────────────────────┘    └────────────────────────────┘    └──────────────┬─────────────┘
                                                                                   │
┌────────────────────────────┐    ┌────────────────────────────┐                   │
│ 5. 运筹重求解与持续演进    │    │ 4. 离线回放与反事实仿真验收│                   │
│ 使用批准冻结的新参数版本求 │◄───│ 在留出集上比对可行率/目标分│◄──────────────────┘
│ 解，支持一键回滚基线参数   │    │ 项/人工接受率，经审批后冻结│
└────────────────────────────┘    └────────────────────────────┘
```

为了防止参数学习把计划员的临时妥协或错误操作当成真理固化进系统，该闭环强制执行五条治理铁律：

1. **可学习范围必须显式声明，硬约束绝不可被训练放宽**：形式化领域模型必须显式标注哪些参数允许被校准（例如：订单交期延误、换产耗时、库存积压、加班时长等目标函数的相对权重，软约束的惩罚系数，经业务批准的弹性容差，以及不影响数学正确性的启发式搜索参数）。**法律法规、安全红线、设备物理容量极限、共享投料口硬上限、物料守恒平衡等硬约束（Hard Constraints），绝对禁止通过参数学习放宽或删除**！
2. **人工调整不是天然的“最优标签”，必须强制进行原因码分类**：计划员手工改动排产表，背后可能有四种完全不同的动机：
   * *动机 A（数据修正）*：发现某张工单的 BOM 或库存主数据错了，手工改计划临时绕开；
   * *动机 B（缺失硬约束）*：现场临时坏了一台模具但还没录入系统，手工把工单挪走（这应当转化为第 14 章的动态硬约束或新领域规则，而不是改权重！）；
   * *动机 C（一次性特批例外）*：老板临时打电话要求某张非紧急订单插队；
   * *动机 D（稳定业务偏好）*：长期稳定的多目标权衡习惯。
   应用层在计划员保存调整时，必须强制记录结构化差异与**调整原因码（Reason Code）**；未分类的人工调整或属于数据修正/一次性例外的样本，严禁作为“最优监督标签”直接混入参数训练集！
3. **训练样本必须包含完整决策上下文且 100% 可回放**：每一个反馈训练样本都不能只保存最终那张人工排产表，而必须同时冻结当时的领域输入快照、运筹模型版本、旧参数版本、运筹原始方案、人工修改方案、审批链以及车间最终的真实执行效果，确保样本在任何时候都能完整回放当时的对比情境。
4. **严格的离线留出集评估与反事实仿真准入**：训练产出的新权重或新罚系数候选值，绝不允许以“在线学习（Online Learning）”的方式直接溜进生产排产！它们必须先在跨时间周期、跨组织和跨场景的留出集（Holdout Set）上进行**历史回放与反事实仿真（Counterfactual Simulation）**，全面比对新旧参数下的方案可行率、各目标分项得分、计划稳定性、人工接受率提升度以及实际执行模拟效果；只有通过安全边界校验并获得业务审批后，才能生成不可变的新参数版本冻结生效。
5. **全链路血缘记录与一键回滚诊断**：每一次排产求解都显式记录所用参数版本的来源与训练数据血缘。一旦外部市场环境剧变、人工偏好转移或新参数导致某项 KPI 退化，系统支持**一键回滚至已批准的基线参数版本**，并能借助诊断工具清晰区分究竟是“目标权重参数失配”、“输入数据质量问题”还是“领域模型缺失了新的硬约束”。

## 第 14 章：智能体原生与业务语义前端 —— 从模糊自然语言到语义中间表示（Semantic IR）

在第 13 章打通了运筹优化（OR）与机器学习（ML）的双向闭环后，接下来我们要迎接“三原生”中的第三极——**智能体原生（Agent-Native）**，并拆解大语言模型是如何作为 `LLM as Runtime` 的**业务语义前端（Semantic Frontend）**，将人类模糊的自然语言意图精准转化为机器可验证的结构化语义中间表示（Semantic IR），并最终编译注入 `ospf` `LinearMetaModel` 的。

### 14.1 给智能体装上“业务词典与语法”：暴露结构化领域元数据、可引用变量、中间值、约束模板与流程契约

为什么许多企业在接入大语言模型后，发现智能体除了能写几句车轱辘话的建议外，根本无法帮计划员生成哪怕一条真正能跑通的排产规则或流程配置？

因为开发者犯了一个根本性的架构错误：**让大语言模型去直接阅读散乱的业务源代码，或者对着贫血 CRUD 接口里含义不明的数据库字段名（如 `col_val_01`、`ext_attr_b`）去盲目猜测业务语义**！

在“智能体原生”架构下，“原生”二字的真正含义是：**形式化领域模型本身就是一份可被智能体直接读取、理解、组合与引用的结构化语义契约**。系统不再把业务知识藏在过程式代码里，而是通过应用层向智能体显式暴露一套机器可读的**结构化领域元数据目录（Structured Domain Metadata Catalog）**——这就好比给智能体装上了一本权威的“企业业务词典与组合语法书”：

```text
                      【面向智能体暴露的结构化领域元数据目录】
                                         │
     ┌───────────────────┬───────────────┼───────────────┬───────────────────┐
     ▼                   ▼               ▼               ▼                   ▼
1. 可引用概念与变量   2. 具名业务中间值 3. 结构化约束模板 4. 可组合流程节点契约 5. 适用边界与错误码
(Variables & Symbols) (Intermediates) (Constraint Tpls) (Flow Node Contracts) (Scopes & Error Codes)
```

具体而言，这份领域元数据目录至少向智能体清晰声明了以下五类核心要素：

1. **领域概念与可引用变量（Referencable Variables）**：明确列出系统中哪些业务对象（产线、设备、物料、订单、工单、库位、运输车次）以及哪些符号变量是允许被引用的（例如 `plannedFeeding[line]`、`plannedFeedingRemaining[line]`、`capacityUsage[resource]`），并严格标注每个变量的 `ospf` 物理量纲（如 `Kilogram`、`Hour`）、索引维度（按产线、按物料、按时间桶）、以及它的状态角色（是计划决策变量，还是只读的已发生事实 `actualFeedingInWindow`）。
2. **具名业务中间值（Named Intermediate Values）**：公开诸如换产时间 `changeoverTime[task]`、生产时长 `productionDuration[task]`、预计投料量 `estimatedFeeding[line]`、估算生产率 `estimatedProductivity[line]` 等中间值的业务含义、计算依赖关系与单位，让智能体在进行原因归因或构造复杂规则时可以直接按名引用。
3. **可用约束模板（Constraint Templates）**：提供经过形式化定义的标准约束骨架，例如线性容量上限约束、资源共享约束、交期时间窗约束、工序前后置关系约束、物料齐套可用性约束以及允许挂载注入的模型位置（Placement / Hook Locations）。
4. **可组合流程节点契约（Flow Node Contracts）**：将原本写死在定制接口里的算法与业务动作，拆解为输入输出契约（I/O Contracts）、前置条件与副作用边界完全透明的标准流程节点——如 `产能估算`、`预测审批`、`数字孪生预计时间推演`、`排产求解`、`替代料分配`、`重算物料消耗预计`、`MRP 缺口计算`、`方案仿真对比` 与 `计划正式下发`。这使得智能体能够针对不同客户的流程差异，像拼装乐高积木一样生成合法的流程编排建议（例如为客户甲编排 `排产 → 替代料分配 → 重算物料消耗 → MRP`，为客户乙编排 `需求预测 → BOM 拆解 → 原料缺口分析 → MRP`）。
5. **适用边界、可选参数与结构化错误码（Boundaries & Error Codes）**：明确声明每项元数据适用的业务组织/租户范围、时间范围粒度、权限要求、生效规则版本以及违反契约时的标准结构化错误码。

### 14.2 结构化推理上下文裁剪：结合当前数字孪生状态、历史快照与异常事件进行影响范围推理

正如我们在第 11 章的依赖推演中所揭示的（第 15 点是第 14 点的前置条件）：**智能体要生成可靠的动态适配方案，必须“先做业务推理，再出适配配置”**。

当计划员向系统提出问题时，智能体不能只对着用户那一句话做字面文本扩写，而必须结合当前正在运行的业务世界进行严密的因果与影响范围推理。为此，应用层会将当前相关的运行态信息经过**上下文裁剪（Context Pruning）与租户/字段权限过滤（Permission Filtering）**后，组装成一份边界清晰的**结构化推理上下文（Structured Reasoning Context）**注入给智能体：

| 推理上下文维度 | 注入的结构化内容明细（以贯穿用例为例） | 在智能体业务推理中的关键作用 |
| :--- | :--- | :--- |
| **1. 当前计划与数字孪生状态** | 产线 A/B 当前生效的基准计划版本；`T1` 实际完工时间（`10:00`，延误 30 分钟）；数字孪生刚重算出的 `T2` 预计开始时间（`10:30`）与 `T3` 计划/预计时间（`11:00`）。 | 让智能体看清“哪些任务已经实际偏离计划”、“偏差沿前后置关系传播到了哪里”以及“后序预计时间是否仍在交付窗口内”。 |
| **2. 已发生的执行事实快照** | 当日时间窗口内已执行任务（如 `T1`）已经实际消耗的投料事实 `actualFeedingInWindow`，以及 WMS 当前可用主料/替代料库存快照。 | 锚定不可篡改的物理事实起点，确保后续生成的约束不会漏算今日已发生的实际投料消耗。 |
| **3. 预测快照与血缘不确定性** | 当前已审批激活的产线有效产能覆盖层（`CapacityEffectiveOverlay`）、底层 `estimatedProductivity[A/B]` 的模型版本、质量评分与置信区间。 | 让智能体在分析排产裕度时，能够引用产能估算的来源与不确定性风险，而不把预测值当成绝对常数。 |
| **4. 生效规则与约束集合** | 当前生效的 BOM 版本、换产时间矩阵、日历规则快照、已激活的硬约束与软约束列表，以及近期发生的设备/物料异常事件。 | 帮助智能体判断 `T2` 顺延后，在资源占用、投料量或换产时间上是否与 `T3` 产生了新的跨线冲突。 |
| **5. 可用操作与工具目录** | 当前用户权限下允许调用的分析工具、仿真沙盒入口、约束模板与流程编排节点契约。 | 严格限制智能体的行动空间，确保其只能推荐系统支持且当前用户有权发起的受控动作。 |

基于这份结构化推理上下文，智能体不再输出模棱两可的散文，而是必须按照契约输出**结构化的推理结果包**：
* **候选原因分析（Candidate Causes）**：指出 `T2` 预计延误 30 分钟是由前序 `T1` 实际完工延误叠加 30 分钟固定换产耗时共同导致；
* **受影响对象集合（Affected Objects）**：精准定位受波及的业务对象集合为 `{任务 T2, 任务 T3, 产线 A, 产线 B, 共享投料口}`；
* **候选动态约束（Candidate Constraints）**：针对用户提出的共享投料口限制，生成绑定了当日时间窗的结构化约束候选；
* **候选应对方案与仿真建议（Candidate Plans & Simulation Proposals）**：提出 `{方案一：仅执行局部推演顺延, 方案二：注入共享投料口约束并触发滚动排产}` 两个对比方案，明确标注各自的风险点与待校验动作，交由应用层发起数字孪生仿真比选。

在整个推理过程中，有一条不可动摇的红线：**智能体推理过程本身绝对不直接修改任何业务状态！它输出的永远是带置信度、可解释、可校验、可审计的“候选判断与待校验动作”，最终采纳哪一个方案，100% 由应用层的确定性校验策略与业务审批决定**。

### 14.3 语义中间表示（Semantic IR）：查询中间表示、约束中间表示与流程中间表示的设计规范

当智能体完成了上下文推理，准备将用户的意图转化为系统可执行的能力（如一次复杂的数据查询、一条动态排产约束、或一段自定义流程组合）时，它输出的结构化候选究竟长什么样？

这就是 `LLM as Runtime` 架构中最核心的平台资产之一——**语义中间表示（Semantic Intermediate Representation, Semantic IR）**。

为什么我们不在智能体和底层执行引擎（数据库、求解器、工作流引擎）之间直接传递 SQL 语句、求解器代码或 JSON 配置文件，而一定要在中间设计一层专门的 `Semantic IR`？
1. **隔离自然语言的模糊性与底层执行引擎的异构性**：自然语言千变万化，而底层可能是关系型数据库、分析型列存、不同厂家的 MILP 求解器或不同的工作流引擎。`Semantic IR` 向上承接大模型抽取出的纯净业务语义，向下通过确定性编译器降阶映射（Lowering）到任意执行后端，实现前后端彻底解耦。
2. **支持规范化（Canonicalization）、内容哈希与热点聚合**：两句表述方式不同、具体参数值不同的自然语言请求（例如“查一下 A 线今天的计划投料”与“看看 B 线明天的计划投料”），在去除具体字面量参数并转换为规范化的 `Semantic IR` 后，具有完全相同的**语义形状（Semantic Shape）**。系统只有基于规范化的 `Semantic IR` 计算形状哈希（Shape Hash），才能准确统计哪些语义模式在运行时被高频重复使用，从而支撑第 16 章的运行时画像与即时编译（JIT）。
3. **提供统一的类型、量纲、权限与版本校验载体**：所有的安全守卫、物理单位检查、租户边界校验与历史版本回放，都统一作用在结构化的 `Semantic IR` 树上，确保没有任何未受检的字符串能够溜进生产环境。

在数字化运营平台（DOP / APS）中，语义中间表示主要包含以下四大标准家族：

| 语义中间表示家族 | 核心结构化要素定义 | 编译降阶目标（Lowering Targets） |
| :--- | :--- | :--- |
| **1. 查询中间表示**<br>（Query IR） | 访问的目标领域实体/视图、投影字段列表、关联关系路径、规范化谓词过滤结构（已剥离具体字面量参数）、分组与聚合算子、排序规则、参数类型签名以及扫描行数/耗时预算（Budget）。 | 参数化 SQL 语句、预编译查询计划（Prepared Plan）、领域视图求值器或受控查询接口插件。 |
| **2. 约束中间表示**<br>（Constraint IR） | 绑定的领域变量与中间值符号、代数与逻辑表达式树（对接 `ospf` `LinearPolynomial`）、比较关系、物理量纲与单位、生效时间窗口、绑定的业务对象集合、软硬优先级以及模型挂载位置（Placement）。 | `ospf` 已编译线性约束（`LinearInequality`），进而注入 `LinearMetaModel` 映射至 MILP、CP 或列生成主/子问题。 |
| **3. 流程中间表示**<br>（Flow IR） | 编排的标准领域流程节点序列、节点间输入输出数据契约映射、前置依赖与分支跳转条件、异常补偿策略、仿真沙盒开关以及必经的人工审批边界。 | 应用层工作流执行计划、滚动排产编排管线或跨系统（ERP/APS/MES/WMS/TMS）协同调度任务。 |
| **4. 策略与参数候选表示**<br>（Policy / Param IR） | 目标函数权重候选、软约束罚系数候选、启发式搜索策略参数、合法取值区间、适用业务场景、支撑样本证据引用与离线评估指标。 | 冻结的运筹优化参数配置版本、局部/全局重排触发阈值策略或预测覆盖层激活快照。 |

---

### 14.4 动态约束转化实战：从“今天 A、B 线共用投料口，总投料不超 1000 公斤”到可哈希、可编译的结构化线性约束候选

为了让你直观感受到“智能体语义前端 + 语义中间表示 + 动态约束编译器”的威力，让我们完整走一遍贯穿全书的标杆场景：**如何将现场人员的一句临时规则，安全编译为 `ospf` 运筹优化引擎中的数学约束**。

```text
┌────────────────────┐    ┌────────────────────┐    ┌────────────────────────┐    ┌────────────────────┐    ┌────────────────────────┐
│   1. 用户业务规则  │    │ 2. LLM 语义前端    │    │    3. 约束中间表示     │    │ 4. 动态约束编译器  │    │   5. 算法执行后端      │
│ “今天A和B线共用投 │───>│ 结合元数据与上下文 │───>│     (Constraint IR)    │───>│ 字段能力与权限校验 │───>│ OSPF LinearInequality  │
│ 料口，不超1000公斤”│    │ 生成结构化候选方案 │    │ 约束定义+表达式+符号引 │    │ + 符号注册表解析   │    │ 注入 LinearMetaModel   │
└────────────────────┘    └────────────────────┘    └────────────────────────┘    └────────────────────┘    └────────────────────────┘
```

#### 第一步：用户用自然语言表达现场规则
周二上午 `10:00`，车间人员输入自然语言：“今天 A 线和 B 线共用一个投料口，总投料不要超过 1000 公斤。”

#### 第二步：大语言模型作为语义前端生成结构化候选
大语言模型读取第 14.1 节暴露的领域元数据目录与第 14.2 节的当前数字孪生上下文，识别出：
* 涉及的业务对象是 `{产线 A (lineA), 产线 B (lineB)}` 及共享资源 `投料口`；
* 时间窗口为 `当日（Day_Current）`，且当前时刻为 `10:00`，窗口内已存在已完工任务的实际投料事实 `actualFeedingInWindow`；
* 限制上限为数值 `1000`、物理单位为质量单位 `千克 (kg)`；
* 对应的约束模板是“时间窗内多产线累计投料容量上限约束”，挂载位置（Placement）为 `排产主模型资源约束区 (MasterResourceConstraints)`。

于是，大模型输出一份标准的**动态约束候选（`Constraint IR`）**。请注意：在这个领域对象与 IR 中，**只描述业务字段语义、物理单位与抽象算法符号，完全不依赖任何具体求解器（如 Gurobi 或 Cplex）的内部实现**：

```json
{
  "irType": "DynamicLinearConstraintCandidate",
  "schemaVersion": "1.0",
  "placement": "MasterResourceConstraints",
  "scope": {
    "tenantId": "factory_01",
    "businessObjects": ["lineA", "lineB"],
    "timeWindow": "2026-09-15T00:00:00Z/2026-09-15T24:00:00Z"
  },
  "lhsExpression": {
    "op": "ADD",
    "terms": [
      { "symbolRef": "actualFeedingInWindow", "bindings": { "lines": ["lineA", "lineB"] }, "role": "ACTUAL_FACT" },
      { "symbolRef": "plannedFeedingRemaining", "bindings": { "line": "lineA" }, "role": "PLANNED" },
      { "symbolRef": "plannedFeedingRemaining", "bindings": { "line": "lineB" }, "role": "PLANNED" }
    ]
  },
  "relation": "LEQ",
  "rhsLimit": { "value": 1000.0, "unit": "kg" },
  "priority": "HARD"
}
```

#### 第三步：严格的边界拦截与动态约束编译
拿到这份结构化候选后，系统**绝不允许未经校验和审批直接编译进生产**。动态约束编译器（Dynamic Constraint Compiler）立即启动多层确定性核验：
1. **负面边界强制拦截**：如果大模型因幻觉引用了领域目录里根本不存在的**未知字段（Unknown Field）**、当前用户无权操作的**未授权字段（Unauthorized Field）**、非法的**未知挂载位置（Unknown Placement）**，或者构造了当前求解器不支持的**非法非线性能力（Unsupported Capability）**，编译器会当场拦截并直接返回结构化错误码，绝不带病执行！
2. **字段能力与物理量纲校验**：编译器核验 `actualFeedingInWindow` 与 `plannedFeedingRemaining` 的物理量纲均为质量（可由 `ospf` 原生 `Quantity` 统一换算为 `Kilogram`），与右端上限 `1000.0 kg` 量纲完全兼容，且状态角色组合合法。
3. **算法符号注册表（Algorithmic Symbol Registry）解析**：在单次排产求解构建期，动态约束编译器向算法层的符号注册表查询并解析 `plannedFeedingRemaining[lineA]` 与 `plannedFeedingRemaining[lineB]`，将它们绑定到当前求解会话中对应的 `ospf` `LinearIntermediateSymbol` 与决策变量上，同时将 `actualFeedingInWindow` 绑定为已冻结的常数项，最终生成不可变的 `ospf` **已编译线性约束（`LinearInequality`）**。

#### 第四步：映射至底层算法执行后端
最后，算法层将这条已编译的 `LinearInequality` 注册进 `LinearMetaModel`，无缝映射至混合整数线性规划（MILP）模型或列生成受限主问题（RMP）中执行求解。

#### 工程实现：基于 OSPF `LinearPolynomial`、`LinearInequality` 与 `LinearMetaModel` 的动态约束编译器完整代码

```kotlin
package org.adaptive.dop.runtime.compiler

import fuookami.ospf.kotlin.utils.math.*
import fuookami.ospf.kotlin.utils.physics.unit.*
import fuookami.ospf.kotlin.utils.physics.quantity.*
import fuookami.ospf.kotlin.utils.error.*
import fuookami.ospf.kotlin.utils.functional.*
import fuookami.ospf.kotlin.core.frontend.expression.monomial.*
import fuookami.ospf.kotlin.core.frontend.expression.polynomial.*
import fuookami.ospf.kotlin.core.frontend.expression.symbol.*
import fuookami.ospf.kotlin.core.frontend.inequality.*
import fuookami.ospf.kotlin.core.frontend.model.mechanism.*
import org.adaptive.dop.domain.role.StateRole
import org.adaptive.dop.infrastructure.ospf.OspfBoundaryAdapter

// 1. 领域元数据目录项 (Field Catalog Entry)：定义智能体允许引用的字段、OSPF 原生单位、状态角色与挂载边界
data class DomainFieldCatalogEntry(
    val fieldName: String,               // 如 "actualFeedingInWindow" 或 "plannedFeedingRemaining"
    val unit: PhysicalUnit,              // 直接使用 OSPF 原生 PhysicalUnit (如 Kilogram, Ton, Hour)
    val role: StateRole,                 // 状态角色 (ActualFactRole / PlannedRole)
    val allowedPlacements: Set<String>,  // 允许注入的模型位置，如 {"MasterResourceConstraints"}
    val authorizedRoles: Set<String>,    // 允许操作该字段的业务角色，如 {"PLANNER", "WORKSHOP_DIRECTOR"}
    val maxSupportedDegree: Int = 1      // 最高支持代数阶数：1 表示仅限线性
)

// 2. 语义中间表示：动态线性约束候选 (Constraint IR)
enum class IrRelationOp { LEQ, EQ, GEQ }

data class ConstraintTermIR(
    val fieldName: String,
    val bindingKey: String,          // 业务对象绑定键，如 "lineA" 或 "lineA_lineB_day1"
    val expectedRoleCode: String,    // "ACTUAL_FACT" 或 "PLANNED"
    val coefficient: Flt64 = Flt64.one
)

data class DynamicConstraintCandidateIR(
    val candidateId: String,
    val tenantId: String,
    val placement: String,
    val timeWindow: String,
    val terms: List<ConstraintTermIR>,
    val relation: IrRelationOp,
    val rhsLimit: Quantity<Flt64>,   // 直接使用 OSPF 原生 Quantity<Flt64> (如 Quantity(Flt64(1000.0), Kilogram))
    val approvedBy: String?          // 生产准入铁律：未经审批不可编译！
)

// 3. 算法符号注册表契约 (Algorithmic Symbol Registry)：
// 将领域字段与对象键解析为单次求解中的冻结常数事实 Quantity<Flt64> 或 OSPF 具名中间符号 Quantity<LinearIntermediateSymbol>
sealed interface ResolvedAlgorithmicSymbol {
    data class FrozenFactConstant(val quantity: Quantity<Flt64>) : ResolvedAlgorithmicSymbol
    data class DecisionIntermediateSymbol(val symbolQty: Quantity<LinearIntermediateSymbol>) : ResolvedAlgorithmicSymbol
}

interface OspfAlgorithmicSymbolRegistry {
    fun resolve(fieldName: String, bindingKey: String): ResolvedAlgorithmicSymbol?
}

// 4. 编译产出的不可变 OSPF 线性约束制品
data class CompiledOspfLinearConstraint(
    val elementId: String,
    val displayName: String,
    val placement: String,
    val ospfInequality: LinearInequality, // 直接产出 OSPF 原生 LinearInequality
    val unit: PhysicalUnit,
    val contentHash: String
)

/**
 * 动态约束编译器 (OspfDynamicConstraintCompiler)：
 * 把守从 LLM 候选语义到 OSPF LinearMetaModel 的确定性生产边界；
 * 对未知字段、未授权字段、未知挂载位置、物理量纲不兼容或未经审批的候选，100% 返回显式 Failed(Err)！
 */
class OspfDynamicConstraintCompiler(
    private val catalog: Map<String, DomainFieldCatalogEntry>,
    private val validPlacements: Set<String>
) {
    fun compileToOspfConstraint(
        candidate: DynamicConstraintCandidateIR,
        callerRoles: Set<String>,
        symbolRegistry: OspfAlgorithmicSymbolRegistry
    ): Ret<CompiledOspfLinearConstraint> {
        // 守卫 1：未经审批的智能体候选严禁编译进入生产
        if (candidate.approvedBy.isNullOrBlank()) {
            return Failed(Err(ErrorCode.ApplicationError, "编译拒绝 [ERR_UNAPPROVED]: 动态约束候选 [${candidate.candidateId}] 未经人工或策略审批"))
        }

        // 守卫 2：拦截未知挂载位置 (Unknown Placement)
        if (candidate.placement !in validPlacements) {
            return Failed(Err(ErrorCode.IllegalArgument, "编译拒绝 [ERR_UNKNOWN_PLACEMENT]: 未知模型挂载位置 [${candidate.placement}]"))
        }

        if (candidate.terms.isEmpty()) {
            return Failed(Err(ErrorCode.IllegalArgument, "编译拒绝 [ERR_EMPTY_TERMS]: 约束左端表达式项不能为空"))
        }

        val targetUnit: PhysicalUnit = candidate.rhsLimit.unit
        val lhsMutablePoly = MutableLinearPolynomial()

        for (term in candidate.terms) {
            // 守卫 3：拦截大模型幻觉捏造的未知字段 (Unknown Field)
            val entry = catalog[term.fieldName]
                ?: return Failed(Err(ErrorCode.SymbolNotFound, "编译拒绝 [ERR_UNKNOWN_FIELD]: 领域目录中不存在字段 [${term.fieldName}]"))

            // 守卫 4：拦截未授权访问字段 (Unauthorized Field) 与挂载位置越权
            if (callerRoles.intersect(entry.authorizedRoles).isEmpty()) {
                return Failed(Err(ErrorCode.ApplicationError, "编译拒绝 [ERR_UNAUTHORIZED_FIELD]: 当前角色无权引用字段 [${term.fieldName}]"))
            }
            if (candidate.placement !in entry.allowedPlacements) {
                return Failed(
                    Err(ErrorCode.IllegalArgument, "编译拒绝 [ERR_INVALID_FIELD_PLACEMENT]: 字段 [${term.fieldName}] 不允许挂载至 [${candidate.placement}]")
                )
            }

            // 守卫 5：校验状态角色代码是否与目录声明一致（防止混淆计划变量与实际事实）
            if (entry.role.roleCode != term.expectedRoleCode) {
                return Failed(
                    Err(ErrorCode.IllegalArgument, "编译拒绝 [ERR_ROLE_MISMATCH]: 字段 [${term.fieldName}] 角色为 ${entry.role.roleCode}，与候选声明 ${term.expectedRoleCode} 不符")
                )
            }

            // 守卫 6：校验物理量纲与右端上限是否兼容（例如左侧各项必须均为质量量纲，可转换为 targetUnit 如 Kilogram）
            if (entry.unit.dimension != targetUnit.dimension) {
                return Failed(
                    Err(ErrorCode.DimensionMismatch, "编译拒绝 [ERR_UNIT_INCOMPATIBLE]: 字段 [${term.fieldName}] 单位 (${entry.unit}) 与右端上限单位 ($targetUnit) 量纲不兼容")
                )
            }

            // 守卫 7：从算法符号注册表解析 OSPF 符号或冻结常数，并执行 OSPF 原生单位换算对齐
            val resolved = symbolRegistry.resolve(term.fieldName, term.bindingKey)
                ?: return Failed(Err(ErrorCode.SymbolNotFound, "符号解析失败: 注册表中未找到 ${term.fieldName}[${term.bindingKey}]"))

            when (resolved) {
                is ResolvedAlgorithmicSymbol.FrozenFactConstant -> {
                    val alignedFact = when (val r = OspfBoundaryAdapter.convertQuantitySafely(resolved.quantity, targetUnit)) {
                        is Ok -> r.value.value
                        is Failed -> return r
                    }
                    lhsMutablePoly += (term.coefficient * alignedFact)
                }
                is ResolvedAlgorithmicSymbol.DecisionIntermediateSymbol -> {
                    val symQty = resolved.symbolQty
                    val oneUnitScale = when (
                        val r = OspfBoundaryAdapter.convertQuantitySafely(Quantity(Flt64.one, symQty.unit), targetUnit)
                    ) {
                        is Ok -> r.value.value
                        is Failed -> return r
                    }
                    // 将 OSPF LinearIntermediateSymbol 按换算系数加入左端多项式
                    lhsMutablePoly += (term.coefficient * oneUnitScale) * symQty.value
                }
            }
        }

        val lhsPoly = LinearPolynomial(lhsMutablePoly)
        val rhsVal = candidate.rhsLimit.value

        // 构造 OSPF 原生 LinearInequality
        val inequality: LinearInequality = when (candidate.relation) {
            IrRelationOp.LEQ -> lhsPoly leq rhsVal
            IrRelationOp.EQ -> lhsPoly eq rhsVal
            IrRelationOp.GEQ -> lhsPoly geq rhsVal
        }

        val elementId = "dyn_c_${candidate.candidateId}"
        val displayName = "动态约束[${candidate.candidateId}]_${candidate.placement}(${targetUnit.symbol})"
        val hash = "sha256:${candidate.tenantId}_${candidate.placement}_${candidate.terms.hashCode()}_${candidate.relation}_${rhsVal}_${targetUnit.symbol}"

        return Ok(
            CompiledOspfLinearConstraint(
                elementId = elementId,
                displayName = displayName,
                placement = candidate.placement,
                ospfInequality = inequality,
                unit = targetUnit,
                contentHash = hash
            )
        )
    }

    /** 将已编译的动态约束直接注入 OSPF LinearMetaModel */
    fun injectIntoMetaModel(metaModel: LinearMetaModel, compiled: CompiledOspfLinearConstraint): Ret<Unit> {
        return when (
            val res = metaModel.addConstraint(
                constraint = compiled.ospfInequality,
                name = compiled.elementId,
                displayName = compiled.displayName
            )
        ) {
            is Ok -> Ok(Unit)
            is Failed -> Failed(res.error)
        }
    }
}
```

## 第 15 章：可信执行边界 —— 从候选语义到生产执行的八步管线与防幻觉护栏

在第 14 章中，我们看到了单次用户意图是如何转化为结构化候选并被编译为数学约束的。但是，在一个多用户、高并发、7×24 小时运转的企业级数字化运营平台（DOP / APS）中，如果我们要把成百上千次这样的日常交互管理起来，并从中筛选出真正有价值的模式沉淀为系统的长期正式能力，就需要一条工业级的**端到端受控编译与发布流水线**，以及一套横切全链路的**形式化安全防线**。

本章将完整拆解从“一次对话交互”到“可沉淀正式能力”的**八步目标架构流水线**，阐述形式化方法、数字孪生沙盒与影子验证如何协同筑起防幻觉护栏，并给出运行时八大核心风险的工程治理方案。

### 15.1 从对话到沉淀能力的八步标准流水线：采集 → 规范化 → 中间表示 → 验证 → 优化 → 降阶映射 → 发布 → 自适应监控

在 `LLM as Runtime` 的目标架构中，任何由用户意图触发并最终走向能力沉淀的过程，都必须严格经历以下由八个标准阶段组成的编译与治理流水线：

```text
┌───────────────────────────────────────────────────────────────────────────────────┐
│ 【阶段 1：采集 (Collection)】                                                     │
│  采集用户原始意图、工具调用轨迹、通用路径执行结果与性能开销事实                   │
└─────────────────────────────────────────┬─────────────────────────────────────────┘
                                          ▼
┌───────────────────────────────────────────────────────────────────────────────────┐
│ 【阶段 2：规范化 (Normalization)】                                                │
│  从原始文本与交互中抽取稳定业务语义结构，剥离具体字面量参数与敏感业务值           │
└─────────────────────────────────────────┬─────────────────────────────────────────┘
                                          ▼
┌───────────────────────────────────────────────────────────────────────────────────┐
│ 【阶段 3：中间表示 (Intermediate Representation)】                                │

                                          ▼
┌───────────────────────────────────────────────────────────────────────────────────┐
│ 【阶段 4：验证 (Verification & Validation)】                                      │
│  执行严格的类型、物理单位、字段目录、租户权限、算力预算、审批状态与语义等价校验   │
└─────────────────────────────────────────┬─────────────────────────────────────────┘
                                          ▼
┌───────────────────────────────────────────────────────────────────────────────────┐
│ 【阶段 5：优化与晋升评估 (Optimization & Promotion Decision)】                    │
│  基于调用频率、延迟、资源成本、稳定性与预期收益，评估是否值得专门化提升           │
└─────────────────────────────────────────┬─────────────────────────────────────────┘
                                          ▼
┌───────────────────────────────────────────────────────────────────────────────────┐
│ 【阶段 6：降阶映射 (Lowering)】                                                   │
│  编译生成参数化查询计划、预编译语句、OSPF 求解器约束模板、规则计划或受控插件      │
└─────────────────────────────────────────┬─────────────────────────────────────────┘
                                          ▼
┌───────────────────────────────────────────────────────────────────────────────────┐
│ 【阶段 7：发布 (Publishing)】                                                     │

└───────────────────────────────────────────────────────────────────────────────────┘
```

让我们逐一审视这八个阶段的核心工程职责：

1. **阶段 1：采集（Collection）** —— 在通用执行路径处理用户请求的同时，运行时无侵入地采集用户意图表达、智能体发起的工具调用链、通用路径返回的业务结果以及实际的执行延迟、扫描行数与算力消耗事实。
2. **阶段 2：规范化（Normalization）** —— 规范化器从原始请求中剥离具体的业务字面量（如将具体的日期 `"2026-09-15"`、具体的产线编号 `"lineA"`、具体的重量 `"1000"` 抽取为类型化参数占位符），并徹底清除任何用户隐私或商业敏感数值，提炼出纯净的**规范化语义形状（Normalized Semantic Shape）**。
3. **阶段 3：中间表示（Intermediate Representation）** —— 将规范化后的语义封装为标准的 `Query IR`、`Constraint IR` 或 `Flow IR`，计算其内容与形状的唯一加密哈希值（Hash）。
4. **阶段 4：验证（Validation）** —— 由确定性验证器执行全方位静态与动态检查：引用的字段是否在当前版本目录中？数据类型与物理量纲（`Quantity`）是否匹配？当前租户与角色是否有权访问这些对象？预计消耗的扫描行数或求解时间是否在预算配额（Budget）之内？是否已获得必要的业务审批？以及该表示与原始意图在业务语义上是否等价？
5. **阶段 5：优化与晋升评估（Optimization）** —— 运行时优化器结合历史画像数据，综合评估该语义形状的调用频率、通用路径延迟、编译维护成本与专门化后的预期收益，决定是让它继续留在通用路径按次执行，还是将其晋升（Promote）进入专门化编译队列。
6. **阶段 6：降阶映射（Lowering）** —— 语义编译器将获准晋升的中间表示降阶编译为具体的目标执行产物，例如数据库的参数化查询计划（Parameterized Query Plan）、预编译语句（Prepared Statement）、`ospf` 动态约束模板、确定性工作流计划或受控插件制品。
7. **阶段 7：发布（Publishing）** —— 新生成的专用能力绝不直接切入生产全量流量，而是必须先经过**影子验证（Shadow Verification）**与小流量**灰度发布（Gray Release）**；验证无误后，进行数字签名与版本号分配，正式写入**计划与能力注册表（Plan Registry）**，并通过原子指针切换接管后续同类请求。
8. **阶段 8：自适应监控与演进（Adaptation）** —— 运行时持续监控已发布专用能力的缓存命中率、执行耗时与结果质量；一旦发现异常支持毫秒级一键回滚；当底层数据库表结构（Schema）、领域字段目录、权限策略或编译器版本发生变更时，精准触发失效标记（Invalidation），自动降级回通用路径并在后台异步触发重新编译。

### 15.2 形式化方法作为横切可信基础：类型、量纲、租户权限、预算配额、前置/后置契约与业务不变量检查

在许多传统软件团队的认知里，“验证（Verification）”往往被等同于代码写完上线前的那道集成测试。但在自适应软件与 `LLM as Runtime` 架构中，**形式化方法与运行时验证绝不是编译完成后的最后一道测试关卡，而是贯穿领域模型、领域语言、事件历史、数字孪生、能力生成与运行时发布的“横切可信基础（Cross-Cutting Trust Foundation）”**。

```text
   ┌─────────────────────────────────────────────────────────────────────────────┐
   │             【横切可信基础：形式化方法与运行时确定性验证守卫】              │
   │  • 代数类型与物理量纲检查 (Type & Dimension Safety)                         │
   │  • 业务不变量与前置/后置契约 (Invariants & Pre/Post-Conditions)             │
   │  • 状态机合法转移与状态角色隔离 (State Machine & Role Isolation)            │
   │  • 租户隔离、字段级权限与算力预算配额 (Tenant, Auth & Resource Budget)      │
   │  • 差分验证、等价性性质测试与影子验证 (Differential & Shadow Verification)  │
   └──┬─────────────┬─────────────┬─────────────┬─────────────┬───────────────┬──┘
      ▼             ▼             ▼             ▼             ▼               ▼
 [领域模型定义] [领域语言描述] [事件历史记录] [数字孪生推演] [产生式编译]   [运行时发布执行]
```

为了确保动态产生的能力在任何时候都不会突破安全红线，系统在全链路强制执行**六条安全边界准则**：

1. **候选层隔离准则**：自然语言文本与大语言模型的原始输出，永远停留在候选层（Candidate Layer），绝不允许作为生产执行主键或直接作为脚本投入运行。
2. **多维静态与动态守卫准则**：任何候选能力进入执行链之前，必须同时通过结构化中间表示校验、代数类型检查、物理量纲与单位兼容性校验、多租户隔离边界检查、字段级读写权限检查、单次计算资源预算（最大扫描行数、最大求解内存与超时上限）检查以及业务审批状态核验。
3. **契约与业务不变量（Invariants）守卫准则**：领域聚合与流程节点显式定义前置条件（Preconditions）、后置条件（Postconditions）与领域不变量（如“任何排产调整不得篡改已发生的实际报工事实 `actualFeeding`”、“库存扣减后可用量不得突破安全底线”）。一旦执行结果违反不变量，事务立即中止并结构化报错。
4. **专用路径零特权准则**：经过专门化编译产生的“专用快路径（Specialized Path）”，**绝对不得绕过“通用慢路径（General Path）”上的任何安全与权限语义**！即使某个专用查询计划已经被预编译并缓存在注册表中，每一次被具体用户调用执行时，运行时依然必须执行最终的租户与字段级授权校验。
5. **动态制品强隔离与可撤销准则**：任何动态编译产生的计划或制品，都必须具备数字签名、版本血缘、资源配额限制，并支持随时一键撤销（Revoke）、运行隔离与安全回滚。
6. **画像隐私脱敏准则**：运行时画像（Profiling）在聚合统计热点模式时，只允许以脱敏后的“规范化语义形状哈希”作为聚合主键，**绝对禁止将完整的用户自然语言原文或包含商业机密的敏感字面量参数作为统计主键持久化**。

### 15.3 在进入生产前证明自己：数字孪生沙盒仿真、通用/专用路径等价性验证与影子运行

当一条由智能体生成的业务调整方案（如追加共享投料口约束并重排）或者一个由语义编译器新编译出的专用执行计划通过了第 15.2 节的静态类型与权限检查后，它距离正式改写生产状态还有最后、也是最关键的一步：**用真实或仿真的运行结果证明自己的正确性与收益**。

根据产物的性质不同，系统分别采用**“数字孪生沙盒仿真比选”**（针对业务决策方案）与**“差分等价性及影子运行验证”**（针对专门化编译能力）两套验证机制：

#### 1. 面向业务决策候选：数字孪生沙盒仿真比选（What-If Sandbox Simulation）
当智能体针对“产线 A、B 共享投料口 + `T1` 延误”提出“方案一：仅局部顺延推演”与“方案二：注入共享投料口约束并触发滚动重排”两个候选方案时，系统绝不会直接在真实生产数据库里去覆盖原计划，而是在可计算的数字孪生沙盒中拉起两个隔离的仿真分支并行试算：

| 仿真比选维度 | 基线计划（原下发计划） | 候选方案一：仅做局部顺延推演 | 候选方案二：注入共享投料约束 + 滚动重排 |
| :--- | :--- | :--- | :--- |
| **数学与物理可行性** | 已失效（因 `T1` 延误且未计入投料口检修限制） | **不可行（违反硬约束）**：`T2` 顺延至 `10:30` 后与 `11:00` 的 `T3` 同时投料，当日累计投料达 `1150 kg > 1000 kg` 上限 | **可行且已证明最优（Optimal）**：求解器微调了 `T3` 的批次投料节奏，当日总投料精准控制在 `995 kg <= 1000 kg` |
| **订单交期准时率** | 100%（基准） | 表面无延期，但现场必然因投料口拥堵停工 | 核心急单 100% 准时，仅非紧急备库工单顺延 40 分钟 |
| **换产总耗时与库存影响** | 换产 60 分钟 | 换产 60 分钟 | 换产 60 分钟，WMS 替代料齐套检查 100% 通过 |
| **计划稳定性（与原计划差异）** | — | 仅改动 1 个任务时间 | 仅局部调整 2 个关联任务，其余 98% 工单保持冻结不动 |

通过这张由数字孪生与 `SolveReport` 自动生成的结构化仿真对比表，计划员无需阅读任何代码，就能一目了然地看出为什么“方案一”会踩中投料口超限的雷区，以及为什么“方案二”能够在守住 `1000 kg` 安全底线的前提下以最小的计划改动化解危机，从而放心地点击审批按钮将“方案二”正式下发生产。

#### 2. 面向专门化编译能力：差分等价性验证与影子运行（Shadow Verification）
当运行时发现某类查询或约束模式反复出现、准备将其编译为“专用快路径”时，系统又是如何防止编译器 Bug 或模型理解偏差把错误固化下来的呢？

系统采用严密的**“异步构建 + 影子验证（Shadow Verification）+ 灰度切换”**三步曲：

```text
                        【新专用计划上线前的影子验证（Shadow Verification）机制】

                                    ┌──> [通用执行路径（权威基准）] ──> 直接向用户返回生产结果
                                    │                                            │
[线上真实业务请求] ──> [流量复制器] ─┤                                            ▼
                                    │                                  (异步比对器：校验结果集、
                                    │                                   状态码、权限边界与性能收益)
                                    └──> [新编译的专用候选计划（影子态）] ────────▲
                                         （异步旁路运行，结果不对外暴露、不写生产库）
```

1. **构建期静态与样本等价验证**：在后台异步编译任务生成专用计划后，计划验证器首先用历史回放样本库对其进行差分等价测试，确认专用计划与通用路径在边界输入下的输出一致。
2. **线上流量旁路影子运行（Shadow Mode）**：进入发布准备阶段后，新计划被标记为 `SHADOW` 状态。当线上匹配该语义形状的真实请求到来时，前台依然 100% 由成熟可靠的**通用路径**处理并向用户返回结果；同时，运行时在后台异步将同一份冻结输入复制一份喂给**专用候选计划**旁路执行（不产生任何外部写副作用）。
3. **零差异证明与收益达标晋升**：影子比对器自动比对通用路径与专用路径的返回结果（或数学约束矩阵）、权限过滤行为以及实际执行耗时。只有当连续 N 次真实影子运行证明**结果 100% 等价（零差异）且性能/成本收益显著高于晋升阈值**时，注册表才将其状态正式切换为 `ACTIVE`（或按 1% → 10% → 100% 灰度放量）；一旦在影子运行中发现哪怕一次结果不一致，该候选计划立即被自动废弃并记录诊断告警，线上业务毫发无损。

### 15.4 运行时八大核心风险治理：防御语义漂移、权限穿透、错误固化、环境变化、代码供应链风险、过度专门化、事件历史失真与仿真失配

在第 4 章中，我们曾剖析了为什么“让大模型直接在线写代码”会死于六大风险；而在第 10 至第 15 章构建起事件溯源、数字孪生、三原生与受控编译流水线之后，我们终于可以在工程上给出涵盖全系统生命周期的**八大核心风险治理矩阵**（包含前文六大运行时编译风险，以及事件历史失真与数字孪生失配两大世界模型风险）：

| 风险类别 | 风险机理与潜在危害 | 在自适应架构中落地的硬核工程治理方案 |
| :--- | :--- | :--- |
| **1. 语义漂移风险**<br>（Semantic Drift） | 同一句自然语言在不同班次、不同上下文中含义不同，模型混淆计划变量与实际事实。 | • 强制转化为显式声明状态角色的 `Semantic IR`；<br>• 绑定版本化领域字段目录；<br>• 依托 `ospf` 强制校验代数类型、物理量纲（`Quantity`）与生效时间范围。 |
| **2. 权限穿透风险**<br>（Privilege Penetration） | 预编译的专用查询计划或约束模板在复用时，错误绕过租户隔离、字段脱敏或算力预算限制。 | • 计划注册表显式绑定权限策略版本；<br>• **每次执行专用路径时强制重新校验最终授权与预算配额**；<br>• 专用路径绝不享有超越通用路径的特权。 |
| **3. 错误能力固化风险**<br>（Error Ossification） | 智能体的一次偶发误判未经严格检验就被沉淀为长期运行的系统模板或规则。 | • 严格执行“候选 → 校验与仿真 → 影子验证/等价验证 → 审批发布 → 一键回滚”全流程边界；<br>• 未通过零差异影子验证与收益阈值的候选严禁转正。 |
| **4. 环境变化失效风险**<br>（Environmental Shift） | 数据库表结构（Schema）、领域目录、权限策略、模型或生成器版本变更，导致旧专用计划失真。 | • 注册表为每个专用计划记录完整的**依赖版本哈希树（Dependency Hash）**；<br>• 任一依赖变更时立即触发精确失效标记（Invalidation），毫秒级自动回退通用路径并异步重编译。 |
| **5. 代码供应链与隔离风险**<br>（Code Supply Chain） | 当高阶专门化生成字节码、JVM 插件或 WebAssembly 制品时，引入非法依赖、越权读写或耗尽宿主机资源。 | • 优先采用低风险的参数化计划与约束模板；<br>• 确需编译代码制品时，强制使用隔离构建进程、制品数字签名、严格依赖白名单、CPU/内存配额限制以及独立类加载器或沙盒进程。 |
| **6. 过度专门化与资源放大**<br>（Over-Specialization） | 低频一次性需求无限生成专用计划与模板，撑爆存储、编译队列与缓存，增加结构熵。 | • 基于热点程度、计算成本与预期收益设定严格的晋升阈值（Promotion Threshold）；<br>• 为构建队列与计划注册表设置硬性数量上限与 LRU/收益淘汰策略。 |
| **7. 事件历史与反馈失真**<br>（History & Feedback Distortion） | 关键事实缺失或未分类的人工计划修补混入样本，导致运行时画像与参数学习归纳出错误模式。 | • 明确不可变事件契约、幂等写入与事件时间（Event Time）语义；<br>• 强制人工调整记录结构化原因码，未分类或数据修正型补丁严禁进入学习训练集。 |
| **8. 数字孪生仿真世界失配**<br>（Simulation Mismatch） | 数字孪生模型参数与车间真实设备节拍、库存或换产耗时长期漂移，导致仿真通过的方案在现实中失败。 | • 利用实际报工反馈持续监控预计时间与实际时间的残差分布；<br>• 定期触发产能与耗时模型校准，并在超出模型适用范围时显式告警降级。 |
