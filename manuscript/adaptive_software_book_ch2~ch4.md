## 第 2 章：从信息化到意图驱动 —— 软件替人类承担了多少认知责任？

在第 1 章的生产调度风暴中，我们看到传统工业软件面对现场变化时的窘境：业务概念在多个系统和算法中各说各话，微小的临时规则调整也不得不排期走完漫长的研发流程。要看清这一困境的历史成因，并找到真正的破局方向，我们需要跳出单点技术的争论，从宏观软件演进史的视角追问一个根本问题：**过去几十年里，软件替人类做的事情究竟发生了什么变化？**

---

### 2.1 软件演进的四个阶段：信息化（记录）、自动化（按规则做事）、前 LLM 智能化（特定判断）与 LLM 智能化（理解目标）

如果我们把企业软件的发展历程拉长来看，它依次经历了**信息化**、**自动化**、**前大语言模型时代的算法智能化**以及**大语言模型时代的智能化**四个阶段。

```text
┌──────────────────┐    ┌──────────────────┐    ┌──────────────────┐    ┌──────────────────┐
│      信息化      │    │      自动化      │    │  前 LLM 智能化   │    │   LLM 智能化     │
│ 把事情记录进系统 │ ──>│ 让系统按规则做事 │ ──>│ 让模型做特定判断 │ ──>│ 理解目标完成任务 │
└──────────────────┘    └──────────────────┘    └──────────────────┘    └──────────────────┘
```

这四个阶段的本质区别，并不在于底层用了关系型数据库、工作流引擎、深度学习还是大语言模型，而在于**软件系统替人类承担了多少“认知与执行责任”**。

#### 第一阶段：信息化 —— 把事情记录进系统
在信息化阶段，软件的核心职责是充当企业的“电子账本”。订单、设备、库存、BOM 与排产计划被录入系统，转化为结构化的业务数据。系统提供的主要能力是记录、查询与跨部门共享，典型输出是各类台账、业务单据与统计报表。在这一阶段，几乎所有的业务认知、逻辑判断与操作执行责任都留在人类身上，人的角色是直接“操作系统”。

#### 第二阶段：自动化 —— 让系统按规则做事
随着业务规模扩大，人们不再满足于手工点按钮流转单据，软件进入了自动化阶段。工程师将明确的业务规则、审批流转与状态触发器写进代码或配置表中，让系统按照既定逻辑自动流转、触发、计算和执行，输出标准化的流程动作或调度任务。此时，系统接管了“确定性规则下的重复执行责任”，但规则本身必须由人类事先穷举并定义清楚，人的角色上移为“设计规则”。

#### 第三阶段：前 LLM 时代智能化（算法智能化）—— 让模型做特定判断
当企业面对设备产能波动、加工耗时预测、物料需求预测或复杂排产优化时，许多规律无法靠人工硬编码规则穷尽，软件随之迈入前大语言模型时代的算法智能化阶段。系统以业务数据加特定数学模型或机器学习模型为输入，承担起识别、预测、推荐与运筹优化的职责，输出分类结果、风险评分或优化计划方案。

在这一阶段，系统开始分担一部分“模式识别与局部寻优的认知责任”，但问题的数学边界、特征口径与约束结构依然必须由算法工程师在开发或训练阶段预先定义完备，人的角色是“定义问题”。

#### 第四阶段：LLM 时代智能化 —— 理解目标并完成任务
大语言模型与智能体（Agent）的到来，开启了第四个阶段。系统接收的不再只是僵化的表单字段或固定格式的算法参数，而是人类的**自然语言意图 + 运行上下文 + 可用工具集**。系统开始具备理解模糊表达、结合上下文推理、自主规划步骤、生成结构化方案并调用既有系统与算法工具的能力，最终输出任务结果或可检验的候选能力。相应地，人类的角色进一步演进为**“表达业务目标 + 审核安全边界”**。

为了直观呈现这四次跃迁，我们可以从核心输入、系统能力、典型输出与人的角色四个维度进行全景对照：

| 演进阶段 | 核心输入 | 系统承担的能力 | 典型输出 | 人的核心角色 |
| :--- | :--- | :--- | :--- | :--- |
| **信息化** | 结构化业务数据 | 记录、查询、共享 | 台账 / 单据 / 报表 | 操作系统 |
| **自动化** | 规则、流程、触发器 | 按既定逻辑自动流转与执行 | 流程动作 / 调度任务 | 设计规则 |
| **前 LLM 时代智能化** | 历史数据 + 特定模型 | 识别、预测、推荐、优化 | 分类 / 评分 / 计划方案 | 定义问题边界 |
| **LLM 时代智能化** | 意图 + 上下文 + 工具 | 理解、推理、规划、生成、调用 | 任务结果 / 候选软件能力 | 表达目标 + 审核边界 |

---

### 2.2 真正的历史断点：软件能力形成的位置，从“发布之前”延伸到了“使用之中”

审视上述四个阶段，为什么前三个阶段的演进主要属于渐进式改良，而第四阶段的到来却引发了软件工程范式的剧震？因为这里出现了一个真正的历史断点：**软件能力形成的位置发生了根本性迁移**。

在信息化、自动化乃至前大语言模型时代的算法智能化中，尽管系统越来越聪明，但“软件能力是如何被制造出来的”这一基本链路从未改变：

```text
【传统软件范式：能力形成于“发布之前”】
业务需求 ──> 产品设计 / 研发排期 ──> 集成开发环境（IDE）中编码 ──> 测试 ──> 构建 ──> 版本发布 ──> 用户使用
```

在这条传统链路里，无论是写死一条数据库校验逻辑、配置一条自动化审批流，还是训练一个产能预测模型、编写一套混合整数线性规划（MILP）排产脚本，**软件能力的形成主要发生在“发布之前”的开发期或训练期**。一旦软件发布上线，它的能力边界就被冻结了；用户在运行现场只能使用研发团队预先设想好的功能。

而在大语言模型时代，一部分“语义生产”与“能力塑造”第一次从开发期跨入到了用户真实使用的运行现场（Runtime）：

```text
【LLM 运行时范式：一部分能力形成于“使用之中”】
用户真实使用 ──> LLM 理解并处理长尾需求 ──> 运行时采集行为与性能事实 ──> 识别高频稳定模式 
──> 抽取语义中间表示（IR） ──> 语义编译与等价性验证 ──> 发布专用确定性能力 ──> 后续请求直接高效执行
```

如上图所示，当用户在生产现场提出一个过去系统里没有现成按钮的长尾诉求（如“今天 A 线和 B 线共用投料口，总投料量不超过 1000 公斤”）时，系统不再直接报错或让你去找研发提工单，而是先由大语言模型在运行现场理解意图、组织上下文并生成结构化候选方案，经安全验证后完成当次处理。紧接着，运行时持续观察这类需求是否在后续生产周期中被反复使用；一旦发现它是一个高频、稳定且收益明确的模式，系统便将其语义结构抽取出来，编译并验证为低成本、可复用的专用确定性能力，后续同类请求直接走专用高效路径执行。

简言之，传统范式是**“先开发，再使用”**；而新的范式在此基础上开辟了第二条通道：**“先在使用中发现和验证需求，再把被证明有效的做法沉淀进产品”**。

### 2.3 传统项目制交付的死结：为什么靠“提需求—写代码—测接口—发版本”永远追不上长尾变化？

理解了“能力形成位置迁移”这一历史断点，我们就很容易看懂为什么传统的工业软件（尤其是涵盖 ERP、APS、MES、WMS、TMS 的数字化运营平台）总是深陷“项目制交付”的泥潭。

制造业与供应链运营天然是一个充满长尾差异与动态扰动的世界：
* **临时性现场异常**：某台关键设备突然降速、某两条产线当天临时共用投料口、某批在途物料因交通管制延误、某张 VIP 客户订单临时插单提前；
* **客户与工厂级特有规则**：不同行业、不同工厂甚至同一工厂的不同生产阶段，在排产先后序、替代料分配策略、齐套检查口径、车辆配载限制与审批流转上都存在大量细微差异。

在传统“发布前定义一切能力”的架构下，软件厂商面对这些千差万别的现场需求，只有两条路可走，而这两条路最终都会走向死胡同：

1. **第一条路：试图在标准产品里预先穷举所有配置开关**。产品经理试图设计出一套包含成百上千个参数开关的超级配置表；结果不仅配置界面复杂到无人能懂，而且一旦遇到第 1001 种现场组合规则（例如跨产线、跨时间窗的动态投料约束），预先写死的开关依然无法表达。
2. **第二条路：退化为“每家客户拉一个项目分支写定制代码”**。现场人员提出问题后，必须依次经过“实施顾问理解 → 产品经理确认 → 研发写接口与分支代码 → 算法工程师改模型 → 联调测试 → 发布上线”的完整周期。

这种把所有现场长尾变化都塞进研发流程的做法，带来了三重不可承受的代价：
* **响应速度与业务时效严重错配**：现场的临时设备异常或急单调整往往要求在几分钟到几小时内给出可行方案，而走完一次代码修改与算法发版动辄需要数天乃至数周；
* **项目定制成本随客户数量线性甚至指数级膨胀**：每交付一家新客户，代码仓库里就多出一堆无法复用的硬编码特例与专用接口，研发团队逐渐被海量项目分支的维护工作拖垮；
* **即使外接了问答式大模型，也未改变能力形成方式**：如果仅仅把大语言模型当作一个帮忙写需求文档或回答操作手册问题的聊天插件，遇到新规则时依然要靠人工改代码、发版本，那么软件的交付成本结构就没有发生任何实质性改变。

要打破这一死结，唯一的出路就是把长尾需求的“探索与初步验证”从高昂的人工研发期卸载到低成本的软件运行时——让通用智能先在现场接住变化，等运行证据证明某项变化确实值得长期保留时，再将其受控地固化为系统能力。

### 2.4 重新定义人与软件的关系：过去用户只是使用程序，未来用户在使用程序的同时也在持续塑造程序

当软件能力的形成从“发布前”延伸到“使用中”，人与软件的关系便迎来了一次深刻的重新定义：

> **过去，用户只是被动地使用已经写好的程序；未来，用户在使用程序的同时，也在持续“编译”和塑造程序——通过日常业务交互，不断告诉软件“这家企业到底应该怎样工作”**。

需要特别澄清的是，这里的“用户在运行时参与编程”或“持续编译程序”，**绝不是指让车间主任、计划员或物流调度员在聊天窗口里手写 Java、Kotlin 或 Python 代码**。业务人员完全不需要懂任何编程语言或数学规划语法。

在新的范式下，人机协同的完整工作闭环由以下五个步骤组成：

1. **用户用业务语言自然表达意图**：业务人员只需像平时沟通一样，用自然语言或日常操作提出业务目标、临时规则、例外情况或决策偏好（例如：“今天 A 线和 B 线共用一个投料口，总投料量不要超过 1000 公斤，T1 已经晚了，帮我看看怎么调”）；
2. **系统将模糊表达转化为可检查的结构化方案**：大语言模型作为语义前端，结合当前领域上下文识别出涉及的产线、任务、资源、时间范围与容量限制，生成机器可严格检查的结构化候选方案（而非直接改动生产数据库）；
3. **在历史数据与数字孪生环境中安全试验**：系统在可推演的生产世界镜像（数字孪生）中先行试算该候选方案，评估其对订单交期、库存齐套、换产耗时与资源冲突的真实影响，并交由优化求解器确认数学可行性；
4. **通过权限、规则与结果校验后受控执行**：只有当字段、物理单位、操作权限、业务不变量和仿真结果全部通过确定性把关（且在必要时获得人工审批确认）后，方案才正式投入排产或执行流程，并全程记录实际运行效果；
5. **反复有效的经验逐步沉淀为正式产品能力**：对于只发生一次的临时状况，系统将其保留为一次性候选配置；对于在同一客户现场反复出现、被运行结果证明长期有效的做法，系统不再每次从头调用大模型重新推理，而是将其逐步升级为客户专用能力、产品可配置能力乃至平台标准核心能力。

由此可见，未来的企业软件不再是一座在交付日就已经封顶的水泥建筑，而更像一个拥有“理解力、记忆力、推演力与自我沉淀机制”的有机体。大语言模型负责低成本地理解人类意图、探索未知的长尾需求；而确定性的软件工程、形式化领域模型与运筹优化算法则负责守住安全底线，并将探索出的真知灼见固化为高可靠的产品资产。

那么，在这套“边使用、边生长”的新范式中，传统的软件代码（Software 1.0）、机器学习模型（Software 2.0）与大语言模型驱动的意图计算（Software 3.0）究竟是怎样的关系？它们又是如何与确定性计算、运筹优化等底层计算范式协同工作的？在接下来的第 3 章中，我们将引入两条正交的进化坐标轴，为您揭晓答案。

## 第 3 章：重读 Software 1.0、2.0 与 3.0 —— 两条正交的软件进化轴

当我们谈论“软件在使用中持续形成自身能力”时，一个最容易引发技术团队争论的问题随之而来：既然大语言模型已经能够理解自然语言意图并驱动计算，这是否意味着传统的硬编码规则与数据库系统（Software 1.0）、以及过去十年大行其道的传统机器学习模型（Software 2.0）即将被淘汰？而在工业制造与供应链领域至关重要的运筹优化（Operations Research, OR）求解器，又该被归入哪一代软件？

为了彻底厘清这些架构迷思，本章将沿着 Andrej Karpathy 提出的 `Software 1.0 → 2.0 → 3.0` 演进脉络，结合企业级核心系统的工程实践，建立一套清晰的**“双正交轴”软件认知框架**。

---

### 3.1 Andrej Karpathy 的三代软件范式：代码定义行为（1.0）、数据塑造行为（2.0）与意图驱动行为（3.0）

2017 年，Andrej Karpathy 提出了著名的 **“Software 2.0”** 概念，用来描述深度学习带来的一种全新软件生产方式：在神经网络中，程序的行为不再由人类工程师显式地逐行编写代码来指定，而是通过收集数据、定义优化目标函数，并利用梯度下降等训练过程，将经验压缩并形成在数以亿计的模型权重（Weights）之中。

到了 2025 年 6 月，Karpathy 在其《Software Is Changing (Again)》演讲中进一步将大语言模型时代定义为 **“Software 3.0”**，指出大语言模型正在成为一种新型计算机形态，而自然语言提示词（Prompts）与上下文开始成为一种全新的编程界面——人类第一次可以直接通过自然语言交互来驱动计算。

如果我们把这一从 1.0 到 3.0 的演进框架引入严肃的企业软件架构，可以用三句极简的判词来概括三代软件的本质特征：

* **Software 1.0：`Code is Program`（代码定义行为）** —— 工程师把确定的业务知识显式写进源代码、规则与查询中；
* **Software 2.0：`Data trains Program`（数据塑造行为）** —— 数据与训练优化过程把历史经验压缩进神经网络或统计模型权重中；
* **Software 3.0：`Intent drives Program`（意图驱动行为）** —— 人的业务意图与运行上下文直接进入软件执行与演化过程。

让我们分别审视这三代软件在企业级系统（如 DOP / APS）中的真实面貌与能力边界：

#### 1. 第一代软件（Software 1.0）：代码定义行为
在 Software 1.0 中，标准的生产路径是：`业务需求 → 系统设计 → 编写代码 / 规则 / 数据库查询 / 算法实现 → 测试 → 发布 → 用户使用`。
* **程序形态与生产者**：程序表现为源代码、业务规则、SQL 查询、有限状态机与显式算法实现，完全由开发者、架构师和算法工程师在开发期亲手编写。
* **核心优势**：确定性极强、行为边界清晰可证、执行性能与资源成本高度可控。在高级计划与排程（APS）及数字化运营平台中，数据库事务、确定性业务计算（如 BOM 展开、精确库存扣减）、显式规则校验、求解器底层适配以及高频查询执行等大量核心能力，今天依然属于 Software 1.0，并且在未来也绝不可替代。
* **固有局限**：Software 1.0 的问题从来不是“不够精准”，而是**“新能力进入系统的主要入口被锁死在研发流程中”**——一旦面对海量的现场长尾差异，需求就必须一次次重走“分析—开发—测试—发布”的重型链路。

#### 2. 第二代软件（Software 2.0）：数据塑造行为
在 Software 2.0 中，形成软件能力的主路径变成了：`历史数据（样本 / 标签 / 特征） → 训练过程（优化目标） → 模型权重（压缩经验） → 在线推理（预测 / 识别 / 估计）`。
* **核心价值**：它改变了“一部分软件行为如何被写出来”的方式。面对从历史生产执行数据中学习设备真实加工时长、评估有效产能、识别交期延误风险或预测市场需求等场景，工程师无需手工穷举成千上万条 `if-else` 规则，而是让模型从历史事实中拟合出统计规律，用带概率与不确定性的输出补充确定性系统无法直接给出的估计。
* **固有局限**：首先，Software 2.0 本质上属于**“训练时编程”**——模型能力通常仍在用户正式使用之前的离线训练阶段形成，运行时只是在调用已冻结权重的模型；其次，**模型权重并不天然等同于业务语义**，如果特征、标签、物理单位、时间窗口与业务对象没有与领域模型严格对齐，模型就会沦为无法解释的黑盒；最后，预测出的产能或耗时数字本身不是行动方案，仍需交由确定性系统或运筹优化模型将其转化为可执行的生产计划。

#### 3. 第三代软件（Software 3.0）：意图与上下文开始驱动行为
在 Software 3.0 中，运行时的基本链路演进为：`用户意图（自然语言目标） + 运行上下文（当前状态 / 历史事件 / 权限边界） → 大语言模型（理解 / 推理 / 规划） → 工具与系统（调用既有能力） → 结构化结果（候选方案 / 受控动作）`。
* **核心突破**：自然语言不再仅仅是发布前给程序员看的“需求文档”，而是开始直接参与运行时的计算与编排。业务人员可以直接表达目标、临时规则、例外情况与偏好，模型则结合当前运行上下文组织既有工具并生成新的结构化执行计划。
* **关键治理前提**：在企业软件中，“意图驱动”绝不意味着自然语言可以绕过系统治理直接改写生产数据；恰恰相反，它的真正价值在于**让用户意图第一次能够在运行时被实时理解并转化为结构化表示，进而驶入可验证、可仿真、可回退的确定性执行链**。

### 3.2 为什么三代软件不是淘汰关系，而是能力形成方式的层层叠加？

在技术演进浪潮中，人们很容易陷入非黑即白的“替代论”误区：当深度学习（Software 2.0）兴起时，曾有人断言传统代码（1.0）将被端到端神经网络取代；当大语言模型（Software 3.0）爆发后，又有声音宣称传统软件工程与机器学习模型都将被一个全能大模型吞噬。

然而在真实的工业级系统中，**三代软件从来不是后浪淘汰前浪的替代关系，而是软件能力形成方式的层层叠加**：

```text
┌─────────────────────────────────────────────────────────────────────────┐
│ LLM as Runtime（运行时持续发现、验证、专门化并沉淀新能力）              │
├─────────────────────────────────────────────────────────────────────────┤
│ Software 3.0：意图驱动行为（理解开放目标、结合上下文规划、生成候选方案）│
├─────────────────────────────────────────────────────────────────────────┤
│ Software 2.0：数据塑造行为（从历史数据学习统计规律、预测产能/耗时/风险）│
├─────────────────────────────────────────────────────────────────────────┤
│ Software 1.0：代码定义行为（确定性计算、状态事务、权限控制、高效执行）  │
└─────────────────────────────────────────────────────────────────────────┘
```

我们可以从以下六个核心维度，清晰地对比三代软件的职责边界与互补关系：

| 对比维度 | Software 1.0（第一代软件） | Software 2.0（第二代软件） | Software 3.0（第三代软件） |
| :--- | :--- | :--- | :--- |
| **主要“程序”形态** | 源代码 / 显式规则 / 数据库查询 | 神经网络与统计模型权重 | 提示词 + 运行上下文 + 工具调用 + 运行时计划 |
| **主要能力生产者** | 人类开发者、架构师、算法工程师 | 历史数据 + 训练优化算法 | 业务用户 + 大语言模型 + 自适应运行时 |
| **能力形成主阶段** | 开发期 / 构建发布期 | 离线训练期 | 运行期 / 人机实时交互期 |
| **最擅长的任务** | 确定性执行、事务保障、低成本高频计算 | 统计规律挖掘、时长/产能预测、风险估计 | 理解开放目标、动态组合能力、处理长尾变化 |
| **典型失败模式** | 面对需求变化僵化，导致反复人工定制 | 数据偏差、分布漂移、输出不确定性、黑盒难解释 | 模型幻觉、越权操作、规划错误、系统结构熵增 |
| **工程治理重点** | 单元测试 / 类型系统 / 版本控制 / 发布流水线 | 数据血缘 / 离线评估 / 漂移监控 / 模型制品治理 | 结构化输出 / 权限校验 / 数字孪生仿真 / 能力沉淀 |

从这张全景对比表中可以得出一个极为重要的架构判断：**从 Software 1.0 到 2.0，主要改变的是“软件能力如何实现”（从手工写规则变成用数据训练权重）；而从 Software 2.0 到 3.0，真正改变的是“软件能力在何时形成、谁可以参与编程，以及编程发生在软件生命周期的哪个阶段”**。

因此，唯有到了 Software 3.0，变革才真正触及了软件的生产方式与全生命周期；而本书所提出的“大语言模型即运行时（LLM as Runtime）”，则是在 Software 3.0“提示词驱动计算”的基础上再向前推进了一大步——将运行时产生的一次性动态意图，置于领域语言、形式化验证、数字孪生仿真与产品线治理的约束之下，实现能力的持续形成、专门化与产品化沉淀。

---

### 3.3 两条正交的演进轴：软件能力形成方式（1.0 → 2.0 → 3.0）vs. 四类计算范式（确定性、运筹优化、机器学习、语义推理）

在规划下一代高级计划与排程（APS）或数字化运营平台（DOP）时，架构师们常常会遇到另一个棘手的分类困惑：系统里同时存在**确定性业务系统**、**运筹优化（OR）**、**机器学习（ML）**和**大语言模型 / 智能体（LLM / Agent）**四类核心计算能力；如果按 Software 1.0、2.0、3.0 来划分，运筹优化究竟属于哪一代？

答案是：**不要试图把四类计算能力强行一对一塞进三代软件的盒子里，因为“软件代际”与“计算范式”根本就是两条彼此正交的坐标轴！**

* **第一条轴（纵轴）：软件能力的形成方式（Software 1.0 → 2.0 → 3.0）** —— 回答的是“软件行为与业务能力是在什么时候、通过什么方式被创造出来的”（是开发期写代码、训练期学数据，还是运行期由意图驱动生成）；
* **第二条轴（横轴）：系统的计算范式（确定性计算 / 运筹优化计算 / 统计与概率计算 / 语义推理计算）** —— 回答的是“当输入确定后，底层引擎采用什么样的数学或逻辑机制来执行计算”。

这两条正交轴的交叉协同关系，可以用如下架构矩阵清晰展现：

| 计算范式 / 核心能力 | 主要计算职责 | 与 Software 1.0 / 2.0 / 3.0（能力形成方式）的正交关系 |
| :--- | :--- | :--- |
| **确定性系统**<br>（数值与状态计算） | 状态管理、数据库事务、权限控制、纯函数业务计算（如 BOM 展开、换产耗时计算）、工作流执行 | **主要由 Software 1.0 承载**，是整个系统稳定运行的基石；同时在 Software 3.0 中，运行时高频查询与动态规则也可被即时编译（JIT）固化为确定性执行计划。 |
| **机器学习**<br>（统计与概率计算） | 有效产能估算、加工时长预测、交期延误风险识别、需求分布建模与不确定性量化 | **典型体现 Software 2.0**（由数据训练形成权重）；但在 Software 3.0 运行时中，它又作为可被智能体与流程编排调用的原生预测与参数校准能力。 |
| **运筹优化**<br>（符号与数学规划计算） | 将业务目标与资源约束形式化为数学规划模型（如 MILP、CP、列生成、Benders 分解），搜索可行解或全局最优解 | **横跨三代软件，绝非单独某一代**：<br>• **在 1.0 方式下**：由算法工程师在开发期固定编写数学模型与硬约束；<br>• **在 2.0 方式下**：引入机器学习预测的分布与不确定集（构建鲁棒/随机优化），或用强化学习加速子问题求解，以及从人工反馈中学习目标权重；<br>• **在 3.0 方式下**：在运行时直接接收由用户自然语言意图编译而成的动态约束与临时目标！ |
| **大语言模型 / 智能体**<br>（语义推理与编排计算） | 理解开放业务目标、结合运行上下文做影响推理、生成结构化候选方案、编排并调用其余三类计算后端 | **典型体现 Software 3.0**：作为把人类意图与上下文带入运行时的总入口，向下协同调度确定性计算、机器学习与运筹优化。 |

这一“双轴正交”模型为我们扫清了最大的架构盲区：未来的工业软件绝不是“用一个大语言模型取代排产求解器和业务系统”，而是**以 Software 3.0 作为运行时语义层与编排入口，将确定性计算、运筹优化、机器学习与语义推理四大计算范式有机统合起来；而每一类计算范式内部的能力，又可以分别通过 1.0（开发期编码）、2.0（训练期学习）和 3.0（运行期意图转化与沉淀）的方式持续形成和演进**。

### 3.4 核心洞察：前大模型时代的传统算法与软件不会被淘汰，而会成为大语言模型的“编译目标”

理解了三代软件的叠加关系与双正交轴模型后，我们就触及了本书关于人工智能落地企业软件的一个核心论断：

> **前大语言模型时代的传统软件工程与算法智能（数据库查询优化器、规则引擎、统计预测模型、混合整数线性规划、启发式算法、工作流引擎与专用代码）不仅不会被淘汰，反而会变得比以往任何时候都更加重要——因为它们将成为大语言模型在运行时的“编译目标（Compilation Targets）”**。

为什么大语言模型不能自己包揽从理解意图到算出最终排产表的所有工作？原因在于两类技术在计算特性上存在着天然的互补性：

* **探索层（大语言模型与智能体）**：大语言模型的强项在于**处理开放性、模糊性与长尾变化**。面对不完整的用户表达、从未见过的新异常场景或跨部门规则协商，它能够以极低的边际成本理解人类意图、组织散乱的上下文并提出结构化的候选方案。但它的短板同样致命：单次推理算力成本高、响应延迟大、输出存在概率波动，且无法对上万个工序变量给出严格的数学可行性与最优性证明。
* **固化层（传统系统与运筹/统计模型）**：数据库查询计划、规则引擎、运筹优化求解器（如 MILP/列生成）、受控预测模型与编译期代码，恰恰具备大模型所不具备的四大工业级品质——**执行结果确定、单次运行成本极低、毫秒至秒级响应、且具备严格的数学可验证性与可审计性**。

因此，在自适应软件架构中，二者之间不是竞争替代关系，而是标准的**“探索—验证—固化”上下游流水线关系**：

```text
┌────────────────────┐      ┌────────────────────┐      ┌────────────────────┐      ┌────────────────────┐
│  1. 新长尾需求出现  │ ───> │  2. 大语言模型探索 │ ───> │  3. 运行证据积累   │ ───> │  4. 传统引擎固化   │
│ 过去无现成产品能力 │      │ 低成本理解并产候选 │      │ 验证稳定性与复用率 │      │ 编译为查询/约束/流 │
└────────────────────┘      └────────────────────┘      └────────────────────┘      └────────────────────┘
```

在这个闭环里，三大角色的职责分工清晰无比：
1. **大语言模型（LLM）负责“发现应该存在什么能力”**：在运行现场接住用户的自然语言目标与临时规则，将其翻译为结构化的业务候选方案；
2. **语义编译器（Semantic Compiler）负责“把它变成什么确定性形式”**：将经过校验的结构化语义，精准降阶映射为参数化 SQL 查询计划、`ospf` 数学约束表达式、运筹求解模型或标准工作流计划；
3. **自适应运行时（Adaptive Runtime）负责“什么时候值得固化、什么时候淘汰失效”**：持续观察运行画像，把高频稳定的任务交给传统系统和运筹算法去高速、低成本执行，并在环境变化时安全回退或触发重新编译。

至此，“大语言模型即运行时（LLM as Runtime）”的轮廓已经呼之欲出。但要让这套架构真正落地生产环境，我们还必须回答一个最尖锐的工程质疑：它与市面上常见的“让大模型在线生成 Python/SQL 脚本并直接运行”究竟有什么本质区别？在接下来的第 4 章中，我们将正面拆解这一核心命题。

---

## 第 4 章：核心命题：LLM as Runtime（大语言模型即运行时）

当业界开始意识到大语言模型能够在运行时动态响应用户需求时，一种极具诱惑力却又极度危险的极简做法迅速流行开来：**既然大模型会写代码，为什么不干脆在系统里开一个聊天框，让大模型根据用户的自然语言直接生成 SQL 查询、Python 排产脚本甚至 Java 业务代码，然后调用 `eval()` 或沙盒解释器直接在线运行？**

在个人桌面小工具或一次性数据分析脚本中，这种“大模型在线写代码并直接执行”的模式或许能带来令人惊艳的演示效果；但在掌管着真金白银订单、万吨级物料投料、数百台产线设备与多租户权限的工业级核心系统（DOP / APS）中，这条路不仅是行不通的，而且是一场彻头彻尾的工程灾难。

本章将系统阐述本书的核心架构哲学——**LLM as Runtime（大语言模型即运行时）**，厘清为什么它绝不是“把集成开发环境（IDE）搬进聊天框”，而是将“语义前端 + 语义中间表示 + 确定性编译器 + 运行画像驱动的即时专门化”引入软件运行时。

---

### 4.1 为什么“把开发工具搬进聊天框、让大模型直接在线写生产代码”在工业界是死路一条？

在严肃的企业软件生产环境中，如果缺乏中间语义层与编译器护栏，允许大语言模型直接把自然语言翻译成任意可执行代码或生产数据库指令，系统将立刻暴露在**六大致命工程风险**之下：

#### 风险一：语义漂移（Semantic Drift）
同一句自然语言在不同的业务上下文、不同的车间班次或不同的时间窗口下，其精确的业务含义可能截然不同。例如，计划员说“今天控制一下 A 线的投料量”，在早班未开工时可能指限制全天的计划投料总量（`plannedFeeding`），而在上午 10:00 产线已运行两小时后，则是指“已发生的实际投料事实（`actualFeedingInWindow`）加上剩余待执行任务的计划投料量（`plannedFeedingRemaining`）”不得超限。若让大模型直接写代码而没有显式的状态角色、单位量纲与版本化目录约束，生成的代码极易出现口径混淆，算出一笔糊涂账。

#### 风险二：权限穿透（Privilege Penetration）
企业核心系统有着极其严密的多租户隔离、部门数据边界、敏感字段脱敏以及算力/预算配额约束。如果允许大模型直接生成原生代码或任意复杂查询并在后端执行，或者在后续把某次生成的脚本缓存起来供他人直接调用，专用执行路径就可能绕过通用路径上的租户过滤、字段级权限检查或审批流，造成严重的数据越权与生产安全事故。

#### 风险三：错误固化（Error Ossification）
运行时动态生成能力最大的风险，还不是大模型偶尔回答错一句话，而是**把大模型的一次幻觉或偶发误判“编译”并固化成了系统的长期正式能力**。如果缺乏人工审批、影子验证（Shadow Verification）、通用/专用路径结果等价性比对以及明确的收益阈值，一次因上下文缺失导致的错误排产逻辑一旦被写入系统规则库，就会在后续每一个生产周期中持续放大错误。

#### 风险四：环境变化与静默失效（Environmental Shift）
企业系统的运行环境处于持续变化之中：数据库的表结构（Schema）会演进、领域字段目录会增删、权限策略会调整、底层优化求解器或预测模型的版本也会升级。大模型在线生成的裸代码片段就像散落在系统里的“黑盒孤儿”，缺乏显式的元数据依赖追踪；一旦底层字段或策略变更，这些代码要么在运行时突然崩溃，要么在毫无察觉的情况下产出错误的业务结果。

#### 风险五：代码供应链与运行隔离风险（Code Supply Chain Risk）
允许动态生成并加载任意代码（如任意 Python 脚本或未受控的字节码插件），意味着攻击者或失控的模型幻觉可能引入未经授权的第三方依赖包、发起非法网络请求、篡改本地文件系统，或者写出死循环耗尽生产服务器的内存与 CPU 资源，直接拖垮核心排产与交易链路。

#### 风险六：过度专门化与结构熵增（Over-Specialization）
如果每一个用户在聊天框里随口提一句一次性、低频次的临时查询或例外规则，系统都不加甄别地为其生成并保存一套专用代码或执行计划，那么不出三个月，系统内部就会堆积成千上万个无人维护的计划碎片。编译、存储、缓存管理与冲突治理的成本将远超动态生成带来的那点收益，软件结构将迅速滑向混乱的“特例垃圾场”。

| 核心风险类型 | 在生产环境中的典型表现 | 必须在架构上建立的治理原则 |
| :--- | :--- | :--- |
| **语义漂移** | 同一句自然语言在不同上下文中含义不同，模型混淆计划与实际口径 | 强制经过结构化中间表示（IR）、版本化目录以及显式类型/单位/范围约束 |
| **权限穿透** | 动态生成的专用计划错误绕过租户、字段级权限或算力预算约束 | 每次执行必须重新校验最终权限；专用路径绝不得绕过通用安全语义 |
| **错误固化** | 大模型的一次偶发幻觉被直接保存并编译成长期运行的系统能力 | 严格执行候选审批、影子验证、结果等价性校验、灰度发布与收益阈值准入 |
| **环境变化** | 数据库结构、字段目录、安全策略或生成器版本变更导致旧计划失真 | 建立显式依赖哈希、精确失效标记（Invalidation）、自动回退与异步重编译 |
| **代码供应链** | 动态插件引入非法依赖、越权访问网络/文件系统或耗尽宿主机资源 | 隔离构建进程、制品数字签名、依赖白名单、资源配额限制与独立类加载器/进程 |
| **过度专门化** | 为海量一次性低频需求生成专用计划，治理与维护成本远超执行收益 | 建立基于热点程度/成本/收益的能力晋升策略，并设置缓存数量与构建队列上限 |

### 4.2 什么是真正的 LLM as Runtime？将大语言模型定位为运行时的“业务语义前端”

既然“让大模型在线写任意代码并直接执行”是一条死胡同，那么本书所倡导的 **LLM as Runtime（大语言模型即运行时）** 究竟是什么？

我们给出其严格的定义：

> **LLM as Runtime 是一种面向自适应软件的架构哲学：编程不再只发生在软件发布前的开发阶段；一部分软件能力将在用户与模型交互的运行时被表达、验证、专门化并持续沉淀。在这一体系中，大语言模型绝不是直接改写生产状态的执行器或求解器，而是运行时的“业务语义前端（Semantic Frontend）”**。

这里的“编程”，是指业务用户在表达目标、业务规则、资源约束和决策偏好的过程中，持续产生新的**“可执行业务语义”**。为了将这些开放、模糊的自然语言安全地转化为工业级软件能力，系统模仿现代编译器的精妙架构，在运行时构建了一条由六个核心环节组成的标准链路：

```text
┌────────────────┐    ┌────────────────┐    ┌────────────────────┐    ┌────────────────┐    ┌────────────────────┐    ┌────────────────────┐
│  1. 用户意图   │    │ 2. LLM 语义前端│    │  3. 语义中间表示   │    │  4. 语义编译器 │    │   5. 受控执行后端  │    │  6. 自适应运行时   │
│ 自然语言/行为  │───>│ 理解与候选生成 │───>│ DSL / AST / 计划IR │───>│ 校验/优化/降阶 │───>│ 数据库/求解器/代码 │───>│ 画像/JIT/失效/回退 │
└────────────────┘    └────────────────┘    └────────────────────┘    └────────────────┘    └────────────────────┘    └────────────────────┘
```

在这条链路中，每个组件各司其职、边界分明：
1. **大语言模型（LLM 语义前端）**：扮演类似编译器前端（Frontend）的角色，负责将用户的自然语言、当前运行上下文、历史交互事件以及领域知识，压缩并翻译为受严格语法约束的结构化候选表示；
2. **语义中间表示（Semantic IR）**：充当隔离自然语言不确定性与底层执行实现的稳定契约层，表现为受约束的领域特定语言（DSL）、抽象语法树（AST）、规范化查询中间表示（Query IR）、动态约束中间表示（Constraint IR）或流程中间表示（Flow IR）；
3. **语义编译器与验证器（Compiler & Validator）**：负责对语义中间表示执行严格的静态与动态检查（涵盖类型、物理量纲、字段目录、租户权限、算力预算与业务不变量），并在通过校验后将其**降阶映射（Lowering）**到具体的目标执行形式；
4. **受控执行后端（Deterministic & Probabilistic Backends）**：由久经考验的数据库查询引擎、规则引擎、`ospf` 与运筹优化求解器（如 MILP/列生成）、受控机器学习运行时或安全代码制品库承担真正的生产级计算与事务执行责任；
5. **自适应运行时（Adaptive Runtime）**：在执行过程中持续采集运行画像（Profiling），决定哪些高频语义模式值得被专门化提升、何时进行影子验证与原子切换、当环境变化时何时标记失效，以及如何在“通用慢路径”与“专用快路径”之间无缝切换。

当我们将这一理念放入企业级数字化运营平台（DOP / APS）的整体顶层设计中时，便形成了一套清晰的**“六层架构语言”**：

| 架构层级 | 核心定位 | 该层级回答的根本架构问题 |
| :--- | :--- | :--- |
| **第一层：长期远景**<br>自适应软件（Adaptive Software） | 长期演进目标 | 未来的企业软件最终应该变成什么样：在使用过程中持续形成、验证并演化自身能力。 |
| **第二层：架构哲学**<br>LLM as Runtime（大语言模型即运行时） | 顶层架构原则 | 当软件能力不再只在发布前形成，运行时应当如何安全地表达、验证和沉淀新能力。 |
| **第三层：核心架构**<br>形式化领域模型 + 三原生（OR / ML / Agent） | 系统语义骨架 | 机器用什么权威业务语言理解世界；业务系统、运筹优化、机器学习与智能体如何共享同一套语义而不发生口径分裂。 |
| **第四层：演进机制**<br>语义编译器 + 自适应运行时 | 能力形成与演化引擎 | 大模型生成的候选语义如何被校验、降阶编译、热点提升、影子验证、精确失效与重新编译。 |
| **第五层：产品演化**<br>软件产品线工程（SPLE） | 产品化治理漏斗 | 哪些运行时专用能力只是局部一次性特例，哪些应当被晋升为客户专用变体、正式产品可变点或平台稳定核心。 |
| **第六层：具体实现**<br>动态查询 JIT / 动态约束编译 / 流程计划 | 工程落地实例 | 上述编译与专门化机制在复杂数据查询、排产动态约束注入与跨系统流程编排等具体场景中如何工程化落地。 |

打一个形象的比方：**“LLM as Runtime”是整座大厦的“屋顶”**，指明了软件长期演进的天际线；**“形式化领域模型（由 `ospf` 等底座承载）”是“语言与类型系统”**；**“三原生（运筹原生、机器学习原生、智能体原生）”是支撑业务运转的“核心运行骨架”**；**“语义编译器 + 运行时专门化”是“能力形成机制”**；**“软件产品线工程”是“产品化晋升机制”**；而动态查询即时编译与动态约束编译器则是跑在这套体系上的具体标杆实例。

### 4.3 为什么它更像“即时编译（JIT）”，而不是“任意代码生成”？

为了帮助软件工程师与架构师更准确地把握 `LLM as Runtime` 的运行机理，我们可以将其与现代虚拟机（如 JVM 或 V8 引擎）中的**即时编译（Just-In-Time Compilation, JIT）**进行对比。

在编程语言虚拟机中，JIT 编译器的核心价值并不是“在运行时随便生成一段机器码”，而是**先通过解释器（通用路径）执行所有代码，同时在运行时收集真实的性能画像（Profiling）；一旦识别出被高频调用的“热点路径（Hot Spots）”，就在后台根据真实的运行类型与分支分布对其进行专门化优化（Specialization），编译成高效率的本地机器码；而当运行时的类型假设被打破（例如加载了新类）时，虚拟机则会立刻触发“去优化（Deoptimization）”，安全回退到通用解释执行路径**。

同理，`LLM as Runtime` 的核心也绝不是“让大模型在线生成任意代码”，而是**根据用户在生产现场的真实使用分布，识别出高频、稳定、可验证的业务语义模式，并将它们从高成本、高延迟的大模型推理路径，专门化提升为低成本、确定性的专用执行能力**。因此，在技术上更精准的术语应当是**语义即时编译（Semantic JIT）**、**软件即时编译（Software JIT）**或**运行画像驱动的专门化（Profile-Guided Specialization）**。

以平台中的“动态查询即时编译”与“动态约束编译”为例，其运作机制与传统虚拟机 JIT 概念存在着严丝合缝的对应关系：

| 传统虚拟机 JIT 核心概念 | LLM as Runtime（语义即时编译）对应组件 | 在企业软件（DOP / APS）中的具体运作机制 |
| :--- | :--- | :--- |
| **解释执行（通用路径）** | 通用语义规划器 / 通用执行路径 | 首次或低频长尾请求先由 LLM 转化为结构化 IR，经校验后走通用查询规划器或通用约束注入路径执行。 |
| **运行时画像（Profiling）** | 规范化语义形状指标采集 | 去除自然语言字面量与具体敏感参数，按**规范化语义形状哈希（Shape Hash）**聚合同类请求，统计调用频率、延迟、扫描行数与求解耗时。 |
| **热点阈值（Hotspot Threshold）** | 能力提升策略（Promotion Policy） | 综合评估某类语义形状的调用热度、执行成本、稳定性与预期收益，达到阈值后将其标记为专门化候选。 |
| **后台异步编译（Async JIT）** | 异步计划构建与降阶编译任务 | 在独立后台任务中，将候选语义 IR 编译为参数化查询计划、预编译语句、结构化约束模板或受控插件，不阻塞前台业务。 |
| **正确性守卫（Guards）** | 计划验证器与影子验证（Shadow Verification） | 新编译的专用计划在正式接管流量前，必须与通用路径并行进行影子比对，证明二者在相同输入下结果等价且权限一致。 |
| **代码缓存（Code Cache）** | 计划与能力注册表（Plan Registry） | 集中管理已发布的专用计划，同时显式绑定数据库 Schema、字段目录、权限策略、编译器与适配器的版本哈希。 |
| **去优化（Deoptimization）** | 精确失效标记、安全回退与重编译 | 当底层数据库表结构、领域字段目录或安全策略发生变更时，注册表精确标记相关专用计划失效，毫秒级自动回退至通用路径并触发后台异步重建。 |

在实际工程落地中，语义即时编译同样遵循**“分层专门化（Tiered Specialization）”**的克制原则——并不是所有热点需求都值得大动干戈去生成字节码或代码插件：

```text
┌────────────────────────────┐      ┌────────────────────────────────────┐      ┌────────────────────────────────────┐
│         第 0 层            │      │              第 1 层               │      │              第 2 层               │
│   通用语义规划器 / 解释器  │ ───> │ 参数化查询计划 / 预编译约束与流程  │ ───> │  受控编译型插件（JVM / WebAssembly）│
│ （处理长尾探索与低频请求） │      │  （风险最低、覆盖 90% 热点收益）   │      │ （仅在性能收益极显著且边界稳定时启用）│
└────────────────────────────┘      └────────────────────────────────────┘      └────────────────────────────────────┘
```

系统总是优先选择风险最低、可回退性最好且收益已经足够的第 1 层确定性产物（如 `查询中间表示 + 参数化查询计划`、或由 `ospf` 承载的 `预编译线性约束模板`）；只有当性能剖析证明某类超高频计算确实存在显著瓶颈、且其产品化边界已经高度稳定时，才按需升级到第 2 层的受控虚拟机插件（如隔离类加载器下的 JVM 插件或 WebAssembly 制品）。

### 4.4 生产执行铁律：自然语言永远停留在候选层，确定性机制负责把守生产执行边界

行文至此，我们已经完整勾勒了第一卷“范式革命篇”的理论主线：从软件四阶段认知责任的演进，到 Software 1.0、2.0、3.0 与四大计算范式的双轴正交，再到 `LLM as Runtime` 的语义即时编译架构。

在结束第一卷、迈向底层形式化领域模型与 `ospf` 建模底座之前，我们必须立下一条贯穿全书、在任何工程妥协下都绝不可逾越的**“生产执行铁律”**：

> **自然语言与大语言模型的原始输出，永远只能停留在“候选层（Candidate Layer）”，绝不能直接成为生产执行指令或生产事实。真正获准进入生产执行链路的，必须是经过严格校验、可哈希、可版本化、可审计、可失效且可回退的结构化语义中间表示（Semantic IR）、确定性计划或受控制品**。

为了确保这条铁律在日常研发与运行中得到 100% 贯彻，系统在“大模型提出候选”与“生产环境正式执行”之间，强制设立了五道不可绕过的确定性防线：

```text
[1. 候选生成] ──> [2. 权限与治理检查] ──> [3. 领域与业务检查] ──> [4. 仿真与结果验证] ──> [5. 版本化与可回退执行]
```

1. **第一道防线：结构化候选隔离** —— 大语言模型和智能体只允许针对受约束的领域元数据输出结构化候选方案；任何未知字段、未授权字段、未知挂载位置或超出底层求解器/系统支持能力的表达，编译器直接拦截并返回结构化错误码，严禁静默猜测或带病放行；
2. **第二道防线：权限、租户与预算把关** —— 系统以确定性代码校验当前发起人是谁、允许访问哪些组织与业务对象、涉及哪些敏感字段、消耗多少算力预算，以及该级别的变更是否必须经过人工审批确认；
3. **第三道防线：领域类型、物理量纲与业务不变量检查** —— 依托形式化领域模型与 `ospf` 基础框架，严格检验候选方案中的数值精度、物理单位兼容性（如拒绝将重量与时间混算）、状态角色合法性（如严禁将预测值或计划值直接覆写为现场实际执行事实）以及业务规则间的自洽性；
4. **第四道防线：数字孪生试算与等价性/影子验证** —— 重要计划调整或新编译的专用能力在投入生产前，必须在数字孪生环境中先行试算（评估交期、库存、产能冲突等全局副作用），或与原通用路径进行影子运行与数学可行性对比验证；
5. **第五道防线：全链路血缘追溯与一键回退** —— 每一个进入生产的动态约束、预测覆盖层或专用执行计划，都必须记录不可变的内容哈希、来源快照、审批链、生效条件与失效边界；一旦外部环境变化或指标异常，系统必须能够毫秒级精准失效并回退到安全的基线路径。

有了这条铁律的守护，大语言模型的“创造力与灵活性”和传统软件工程的“严谨性与确定性”终于不再对立。

しかし，巧妇难为无米之炊。如果系统底层依然是一盘散沙的贫血 CRUD 表结构和各说各话的黑盒算法脚本，那么无论上面的语义编译器和运行时设计得多么精妙，大模型转换出来的意图依然找不到一个统一、精确的着陆场。我们究竟该如何为业务系统、运筹优化、机器学习和智能体打造一套共同的“世界语言与数学底座”？

从下一章开始，我们将正式进入本书的**第二卷：语义底座篇**，深入探索“三原生统一于形式化领域模型”的核心架构，并亲手揭开开源运筹与领域建模框架 `ospf` 的神秘面纱。
