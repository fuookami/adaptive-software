## Original structure（供译者对照，译文就绪后删除本节）

- 1.1 一场横跨 ERP、APS、MES、WMS、TMS 的急单风暴：为什么系统越建越多，现场排产却越来越累？
  - 内耗一：同一个业务概念，全公司有六套口径
  - 内耗二：微小的现场规则变化，被迫走完漫长的研发流程
  - 内耗三：系统只知道“现在是什么”，却患上了“过程失忆症”
  - 内耗四：看得见当前异常，却不敢安全推演“如果这样做会怎样”
  - 内耗五：接入了大语言模型，却只停留在“聊得很热闹的文字建议”
  - 内耗六：一次性的聪明适配，无法沉淀为长期复用的产品资产
- 1.2 传统贫血 CRUD 架构的局限：散落在应用服务、数据库脚本、报表与人工经验里的业务口径
  - 1. 业务规则与持久化、框架强耦合，丧失独立测试与轻量仿真能力
  - 2. 裸数值（Raw `Double`）与无量纲传输，编译期对单位错配毫无察觉
  - 3. 缺乏状态快照与三层时间语义，滚动排产沦为“黑账”
  - 4. 智能体面对贫血接口，只能“盲人摸象”
- 1.3 “外挂黑盒算法服务”的七大工程痛点：拼装数据成本高、无状态难感知与中间值不可解释
  - 痛点 1：算法服务无状态，数据微调也需全量拼装请求
  - 痛点 2：简单计算被迫走重型算法接口，“拼装数据两小时，计算只要五毫秒”
  - 痛点 3：算法内部私藏业务知识，系统沦为“看不懂规则的传声筒”
  - 痛点 4：中间值被封闭在算法黑盒内，结果无法查询、解释与复盘
  - 痛点 5：同一概念在系统与算法中重复编码，口径必然分叉
  - 痛点 6：外部黑盒机器学习缺乏领域语义与版本治理，预测不敢进生产
  - 痛点 7：求解结果退化为“成功/失败”字符串或原始日志，无法自解释
- 1.4 两个相互咬合的根问题：领域知识由谁统一表达？新的领域能力如何进入系统？
