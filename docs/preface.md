# 前言与全书导读：当用户在使用软件的同时，也在“编译”软件

## 一、 为什么写这本书？

过去半个世纪里，无论开发语言、框架与软件工程方法论如何迭代，企业软件的生产方式始终遵循着一条铁律：**软件能力主要在“发布之前”的开发阶段形成**。需求经过产品设计、工程师在集成开发环境（IDE）中编码、测试、构建与发布后进入生产系统，用户随后使用这套已经定型的程序。一旦业务现场出现开发期未能预见的临时规则、流程差异或客户化长尾需求，团队就不得不再次启动“提需求—排期—写代码—联调—发版”的漫长循环。

大语言模型（LLM）的出现，第一次在根基上撼动了这一假设。

如果把 Andrej Karpathy 提出的软件演进脉络放在企业级系统的视角下审视，我们会发现：Software 1.0 把业务知识显式写进代码与规则；Software 2.0 通过数据、目标函数与训练过程把经验压缩进神经网络权重；而到了 Software 3.0 时代，自然语言与运行上下文开始成为新的编程界面。从 Software 1.0 到 2.0，改变的主要是“软件能力如何实现”；而从 Software 2.0 到 3.0，真正发生断裂的是**“软件能力在何时形成、由谁参与创造，以及编程发生在什么阶段”**。

然而，当无数团队试图把大语言模型引入高级计划与排程（APS）、制造执行（MES）、仓储管理（WMS）、运输管理（TMS）等严肃的企业运营核心系统时，却迅速撞上了两堵高墙：

第一堵墙是**“语义分裂之墙”**。同一个“产能”“投料量”“换产时间”或“时间窗口”，在业务系统里是数据库字段与数值计算，在运筹优化（OR）里是决策变量与数学约束，在机器学习（ML）里是统计特征与预测标签，在大语言模型里则是自然语言提示词。当四套计算范式各说各话时，系统不仅难以协同，还会因规则更新频繁出现口径事故。

第二堵墙是**“生产信任之墙”**。大语言模型擅长处理开放、模糊与长尾的意图，但它本质上是概率生成模型，存在幻觉、语义漂移与越权风险。在真金白银运转的工厂与供应链现场，企业绝不可能允许大模型因为一句自然语言就直接改写生产状态，更不能把“LLM as Runtime”简单粗暴地理解为“让大模型在线写任意代码并直接执行”。

这本书正是为了回答如何翻越这两堵高墙而写。

## 二、 本书的核心思想

本书提出并系统阐述了一套面向下一代企业软件的完整架构体系，其核心命题可以浓缩为一句话：

> **过去，用户使用程序；未来，用户在使用程序的同时，也在持续“编译”程序——这里的编译，是把运行时的开放意图转化为可验证、可版本化、可回退的确定性软件能力，而不是在线执行任意代码**。

围绕这一命题，全书构建了三层架构定位与两个演进闭环：

1. **长期远景：自适应软件（Adaptive Software）**。大语言模型的战略价值不只是充当一个更聪明的聊天窗口，而是推动软件从“一次性交付的静态程序”演进为“在使用过程中持续形成、验证与优化自身能力的自适应软件”。
2. **核心架构：三原生统一于形式化领域模型**。运筹原生（OR-Native）、机器学习原生（ML-Native）与智能体原生（Agent-Native）共享同一套以 `ospf` 等形式化计算底座承载的领域模型，分别对同一业务语义进行符号解释、统计/概率解释与语义解释，并与系统侧的确定性数值解释严格对齐。形式化领域模型既是跨范式协作的共同契约，也是运行时的领域语言规范、类型系统与编译契约。
3. **演进与治理机制：语义即时编译（Semantic JIT）+ 软件产品线工程（SPLE）**。大语言模型在运行时仅承担“语义前端”，负责生成结构化候选表示（Semantic IR）；编译器与验证器结合事件溯源（记忆过去）与数字孪生（推演未来），将候选降阶映射为确定性的查询计划、数学约束或工作流；自适应运行时根据运行画像识别高频稳定模式并完成热点专门化；最终，软件产品线工程负责将经过重复证据验证的能力，按“临时能力 → 客户专用能力 → 产品可变点 → 平台稳定核心”的四级阶梯吸收进长期产品结构，避免系统因无限动态化而陷入结构熵增。

## 三、 读者对象与阅读路线建议

本书面向两类核心读者，您可以根据自身背景选择最佳阅读路径：

* **如果你是架构师、后端研发工程师、运筹算法工程师或 AI 智能体开发者**：建议按从第一卷到第五卷的顺序完整阅读，重点关注第二卷（形式化领域模型与 `ospf` 数值/量纲/表达式双入口底座）、第三卷（DDD 白盒算法编排、列生成/Benders 分解与 `SolveReport` 正交诊断）以及第四、五卷的语义编译流水线实现。
* **如果你是 CTO、技术管理者、数字化负责人、产品经理或工业软件业务专家**：建议重点阅读**第一卷（第 1～4 章）**、**第三卷的第 9～10 章**以及**第五卷的第 17～18 章**。这些章节刻意剥离了底层数学推导，从软件演进规律、成本结构重塑、安全治理边界与产品资产沉淀的视角，为您勾勒出从“项目定制泥潭”走向“平台能力运营”的完整蓝图。

现在，让我们先推开一家现代化制造企业的计划调度室大门，看一看在传统软件架构下，一场再普通不过的现场变化是如何演变成全链路系统风暴的。
