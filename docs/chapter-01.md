# 第 1 章：被“增删改查”与“外挂黑盒”困住的企业软件

在几乎所有工业软件与供应链系统的宣传册里，数字化运营平台（DOP）都被描绘成一幅秩序井然的图景：企业资源计划（ERP）统管主数据与主计划，高级计划与排程（APS）精准求解每一台设备的工序，制造执行系统（MES）实时采集产线进度，仓储管理系统（WMS）把控物料齐套，运输管理系统（TMS）调度车辆发运。

然而，一旦走进真实的生产现场就会发现，许多上了全套信息化与算法系统的企业，计划员与研发团队反而做得越来越累。每当现场出现一点风吹草动——一条产线延误、两个车间临时共用一个投料口、一批原料改用替代料——原本号称高度协同的系统群就会迅速退化为彼此割裂的信息孤岛，最终不得不靠计划员导出 Excel 手工调整，或拉起研发团队花上几周时间修改代码与算法接口。

为什么系统越建越多、算法越引越贵，软件适应变化的能力却依然如此脆弱？本章将从一场真实的生产排程风暴切入，剖析传统“贫血增删改查（CRUD）”与“外挂黑盒算法”架构的深层病灶，并揭示下一代企业软件必须回答的两个根源问题。

---

## 1.1 一场横跨 ERP、APS、MES、WMS、TMS 的急单风暴：为什么系统越建越多，现场排产却越来越累？

让我们把目光投向某制造工厂一个周二上午 10:00 的生产调度现场。

工厂里有两条主力产线：产线 A 和产线 B。按照早班下发的排产计划，产线 A 上的前序任务 `T1` 原定于 `08:00` 开始、`09:30` 结束，紧接着从 `10:00` 开始执行后序任务 `T2`（中间预留 30 分钟换产时间）；产线 B 则计划在 `11:00` 启动任务 `T3`。与此同时，MES、WMS 与 TMS 正在各自记录现场的执行事实，APS 则需要消费这些系统的同步结果，计算它们对库存、产量和交付进度的实际影响。

上午 10:00 整，三个变化同时砸向了计划员的工作台：

1. **MES 报工延误**：产线 A 的前序任务 `T1` 实际在 `08:10` 才启动，直到 `10:00` 才刚刚完工，比原计划整整晚了 30 分钟。
2. **现场临时设备受限**：车间主任打来电话，由于一套供料设备临时检修，今天产线 A 和产线 B 必须**共用同一个投料口**，且当天两条产线在该投料口的总投料量不能超过上限 `1000 公斤`（`feedingLimit = 1000 kg`）。
3. **WMS 替代料切换**：仓库反馈部分原定主料批次尚未到齐，刚对计划任务执行了替代料分配；替代料更新了计划任务的投料配比后，亟需重新核算物料消耗预计与后续 MRP 缺口。

面对这局面，计划员对着系统说出了一个在业务上再自然不过的诉求：

> “产线 A 和 B 今天共用一个投料口，总投料不要超过 1000 公斤；现在 T1 已经延误了，加上刚换了替代料，帮我看看后面哪些任务和订单交付会受影响？我们是只做局部调整就行，还是得重新跑一次滚动排产？”

就是这样一句在人类计划员听来清晰明了的话，却让传统软件系统瞬间陷入了瘫痪，暴露出日常运营中令业务与研发疲于奔命的**“六大业务内耗”**：

### 内耗一：同一个业务概念，全公司有六套口径
要回答计划员的问题，首先得算清楚“投料量”“生产时长”“产能”“库存可用量”和“换产时间”。但在现有体系里，这些核心概念散落在六个不同的角落：
* **业务系统（ERP/MES/WMS）**里有一套用 Java/SQL 写的数值计算逻辑；
* **排产算法（APS 求解服务）**里有一套用 Python/C++ 写的数学约束表达式；
* **机器学习模型**里有一套按特征工程脚本切分的历史产能与耗时口径；
* **BI 报表**、**项目配置文件**以及**老计划员的个人经验表**里，还各自维护着不同的折算系数。

一旦工艺规则或替代料损耗率微调，只要有一处没有同步修改，就会出现“大家嘴里说的都是‘投料量’，但系统算出来的预计消耗、算法约束里的计划投料、以及报表里的实际统计根本对不上号”的荒诞局面。表面上看这是数据同步或接口联调问题，根源上则是**企业缺少一个统一、权威、可直接被各系统与算法共同消费的业务知识来源**。

### 内耗二：微小的现场规则变化，被迫走完漫长的研发流程
“今天 A 线和 B 线共用投料口，总量不超 1000 公斤”——这是极其典型的生产现场长尾规则。此外，诸如某台设备临时限速、某个急单插单、某类物料当日限用、某个客户要求特殊审批流等变化，在工厂里每天都在发生。

然而在传统软件架构下，如果当初开发时没有预先在数据库和算法接口里写死“双线共享投料口上限”这个参数开关，这项需求就只能走标准研发链路：

```text
现场提出问题 → 实施顾问理解 → 产品经理确认 → 后端开发改接口与表结构 → 算法工程师改数学模型 → 联调测试 → 版本发布
```

对于构建全新的平台标准能力，这套流程无可厚非；但如果连现场临时维持一两天的工艺限制都要排队等研发发版，等代码上线时，那批订单早就交货或违约了。

### 内耗三：系统只知道“现在是什么”，却患上了“过程失忆症”
当看板上弹出红色预警“任务 `T2` 预计延期 45 分钟”时，系统展示的仅仅是一个孤立的当前状态（`What is?`）。但计划员与管理者真正需要追问的是“为什么会变成这样”（`What happened?`）：
* 是因为前序任务 `T1` 报工晚了，还是因为 WMS 配送缺料？
* 是设备突发故障，还是早班计划员手工拖拽过工单顺序？
* 当时排产激活的是哪一版产能预测快照？哪条约束规则起了决定性作用？

如果系统只用数据库覆盖保存最新状态，而不保留不可变的领域事件、决策依据、人工调整原因与规则版本时间轴，系统就既无法完成可靠的历史复盘，也无法为机器学习与后续优化提供干净的经验样本。

### 内耗四：看得见当前异常，却不敢安全推演“如果这样做会怎样”
面对 `T1` 延误和投料口受限，计划员脑中会闪过好几种应对假设（`What if?`）：如果只把后序任务顺延半小时呢？如果把部分任务切到其它资源呢？如果不触发全局重排、只做局部调整，会不会把交期风险掩盖掉？

但在传统系统中，由于缺乏可独立计算的生产世界镜像（数字孪生），计划员要想看一眼调整后的连锁反应，往往只能直接修改正式计划或重新调用沉重的全局排产接口——直接改正式计划风险极高，而每次微调都跑一遍全局算法又慢得难以忍受。

### 内耗五：接入了大语言模型，却只停留在“聊得很热闹的文字建议”
不少企业尝试引入大语言模型助手。当计划员把上述问题发给聊天框时，大模型确实能读懂字面意思，甚至给出一段看似头头是道的文字回复：“建议您关注 T2 和 T3 的交期，并控制 A、B 产线的投料节奏”。

但这种自然语言建议无法直接转化为生产生产力：大模型既不知道系统里“计划投料量”对应的准确变量名与计量单位，也不知道当天已经实际发生了多少投料（`actualFeedingInWindow`），更无法保证它拍脑袋生成的调整建议符合产能硬约束与权限边界。没有结构化校验、仿真试算与运筹求解器把关，谁敢让一段聊天文本直接去改工厂的排产指令？

### 内耗六：一次性的聪明适配，无法沉淀为长期复用的产品资产
退一步讲，即便依靠智能体或驻场工程师的临时配置，好不容易帮客户处理了这次“共享投料口”限制。到了下周、下个月，当同一家工厂再次启用该规则，或者另外十家同行业客户也提出高度相似的“多产线共用前处理资源”需求时，系统依然是在从零重新推理或重复写项目补丁。一次性动态适配没有晋升通道，项目交付的代码分支越积越多，产品本身却没有变得更成熟。

## 1.2 传统贫血 CRUD 架构的局限：散落在应用服务、数据库脚本、报表与人工经验里的业务口径

为什么上述六大业务内耗在企业软件中如此普遍？当我们剥开业务表象、深入代码仓库内部时，首先看到的就是统治了企业级开发二十余年的**传统“贫血增删改查（Anemic CRUD）”架构**。

需要明确的是，这里反思的并不是作为表现层或接口层模式的 MVC（模型-视图-控制器）本身——MVC 完全可以与领域驱动设计（DDD）良好共存。真正导致系统腐化的，是常见的 `Controller -> Service -> DAO` 贫血组织方式：领域对象退化为只有 Getter/Setter 的数据库表映射结构（PO/DTO），而将复杂的业务规则、计算公式和状态流转全部隐式揉杂在冗长的应用服务（Service）过程代码与数据库访问（DAO/SQL）脚本中。

在简单的行政办公或单据流转系统中，贫血 CRUD 或许能够应付；但以 APS 及数字化运营平台（DOP）为代表的核心系统，其本质从来不是简单的“增删改查”，而是由一系列高密度计算、约束求解与推演构成的复杂闭环：

* **基础业务计算**：BOM 树展开与数量累乘、投料量计算、替代料分配后的物料消耗预计、设备换产时间计算、工单生产时长计算、日历可用性与产能占用计算；
* **约束与优化求解**：资源容量约束、动态业务约束注入、排产数学建模与求解、滚动计划修正；
* **动态推演与数据智能**：生产计划数字孪生推演、基于历史事实的数据驱动估算与预测、机器学习模型制品与回放治理；
* **语义协同与运行时演化**：智能体业务推理、基于元数据的动态适配、语义中间表示（Semantic IR）与受控编译、运行时画像采集与能力专门化沉淀。

当研发团队试图用传统的贫血 `Service + DAO + DTO` 模式去承载上述能力时，立刻会遭遇四重结构性困境：

### 1. 业务规则与持久化、框架强耦合，丧失独立测试与轻量仿真能力
在贫血架构中，一段“计算后序任务预计开始时间”或“核算物料消耗”的逻辑，往往夹杂在某个上千行的 `ScheduleService.updatePlan()` 方法里，中间穿插着多次数据库查询、事务提交与消息发送。想要验证一个换产时间规则的改动是否正确，开发者必须启动完整的 Spring 容器、连接测试数据库、甚至启动远程算法服务才能跑通集成测试。由于计算逻辑没有被提炼为无副作用的纯函数与独立领域计算模型，系统根本无法在不污染真实数据库状态的前提下，在内存中对多个假设方案进行高频、轻量的仿真试算。

### 2. 裸数值（Raw `Double`）与无量纲传输，编译期对单位错配毫无察觉
贫血服务层与数据传输对象（DTO）通常直接使用裸浮点数（如 `Double` 或 `BigDecimal`）传递数值。字段名叫 `feedingAmount` 或 `capacity`，至于它的物理量纲究竟是“千克（kg）”还是“吨（t）”、是“千克/小时（kg/h）”还是“件/班次”，全靠程序员写注释或口头约定。当 ERP 传过来的订单数量、WMS 传过来的库存重量与 APS 内部的节拍时间混在一起运算时，哪怕发生了“把千克与小时直接相加”或“摄氏度等仿射单位被直接乘除”的低级错误，编译器也无法拦截，最终演变成隐蔽的线上排产事故。

### 3. 缺乏状态快照与三层时间语义，滚动排产沦为“黑账”
贫血 CRUD 天然围绕“当前态覆盖更新（Update in-place）”设计：一张工单表里往往只有一组 `start_time` 和 `end_time` 字段。然而在真实的滚动排产与数字孪生场景中，同一个工单必须同时区分三类截然不同的时间角色：

| 时间角色 | 业务含义 | 数据来源与更新机制 |
| :--- | :--- | :--- |
| **计划开始/结束时间** | 排产方案正式下发时生成的基准计划 | 由排产方案版本冻结保存，作为考核与对比基准 |
| **预计开始/结束时间** | 根据当前最新执行进度动态推算出的未来预测 | 前序任务实际时间更新后，由领域计算模型自动向后传播重算 |
| **实际开始/结束时间** | MES 或车间现场反馈的真实物理执行时间 | 由外部执行事实入口单向记录，不可由算法或预测伪造 |

如果只围绕当前态增删改查而不区分“计划、预计、实际”三层状态角色，也不冻结每轮计算的输入快照与规则版本，一旦前序任务延误或触发重排，系统就会用当前主数据覆盖历史状态，再也无法解释“为什么上一轮计划是那样、这一轮计划变成了这样”。

### 4. 智能体面对贫血接口，只能“盲人摸象”
到了 Software 3.0 时代，贫血 CRUD 的缺陷被进一步放大。当我们希望大语言模型或智能体协助分析异常、生成动态约束或编排流程时，如果系统只暴露一堆贫血的 REST 接口与数据库列名，智能体根本无从知晓某个字段背后的业务含义、允许引用的符号变量、中间值计算来源、单位边界以及流程节点的输入输出契约。让大模型去读散乱的业务代码或猜表字段，其结果必然是停留在不着边际的自然语言建议，或者生成无法通过系统校验的非法参数。

## 1.3 “外挂黑盒算法服务”的七大工程痛点：拼装数据成本高、无状态难感知与中间值不可解释

如果说系统侧的贫血 CRUD 造成了业务语义的空心化，那么工业软件中普遍采用的**“业务系统 + 外挂无状态算法服务”**二元割裂模式，则是导致系统与算法长期“两张皮”的直接推手。

在过去的开发模式中，由于后端工程团队与运筹算法/数据科学团队使用不同的技术栈，架构上通常会把排产求解、统计估算和推演逻辑全部塞进一个独立的无状态算法服务里，通过定制的 HTTP/RPC 接口（传入巨大的 JSON/DTO，返回结果摘要）与业务系统交互。这种看似“职责清晰”的外挂黑盒模式，在实际演进中引发了十一个环环相扣的工程痛点（其中前七项直接制约日常研发与运行，后四项则彻底锁死了系统的智能化演进空间）：

### 痛点 1：算法服务无状态，数据微调也需全量拼装请求
外挂算法服务本身不管理业务状态与生命周期；当车间现场某台设备状态变更或某个工单报工更新时，算法无法自然感知，必须由业务系统从几十张数据库表中重新查询、过滤、拼装出全量请求数据并重新发起调用。

### 痛点 2：简单计算被迫走重型算法接口，“拼装数据两小时，计算只要五毫秒”
许多原本属于确定性业务计算的逻辑被错误地关进了算法服务。例如：
* 在需求预测中按 BOM 将成品拆解为原料需求数量，本质上只是清晰的 BOM 树遍历与数量累乘；如果这也要调用完整的 MRP 算法服务，后端为 MRP 拼装全套请求结构体的数据准备成本，往往远大于实现 BOM 拆解计算本身。
* 排产完成后执行替代料分配，更新了计划任务投料后，只需重新计算物料消耗预计；但如果物料消耗预计公式只写在算法服务内部，后端就只能重新拼装整套算法计划任务并再次调用远程接口。

### 痛点 3：算法内部私藏业务知识，系统沦为“看不懂规则的传声筒”
在数字孪生动态推演中，当前序任务 `T1` 产生实际开始/结束时间后，后序任务 `T2` 的预计开始/结束时间理应按以下领域公式动态更新：

```text
后序任务预计开始时间
= 前序任务实际结束时间
+ 前序任务到后序任务的换产时间
+ 日历可用时间调整

后序任务预计结束时间
= 后序任务预计开始时间
+ 后序任务生产时长
+ 班次 / 休息 / 停机时间调整
```

其中，换产时间与生产时长的计算关系分别为：

```text
换产时间 = f(前一物料, 后一物料, 设备, 工艺规则)
生产时长 = f(生产数量, 设备产能, 工艺节拍, 班次日历)
```

如果这些计算知识只被封装在排产算法黑盒内部，业务系统自己根本读不懂也算不出换产时间与生产时长，导致哪怕只是局部的进度偏差传播，系统也无法独立推演，只能一次次重调完整的排产算法。

### 痛点 4：中间值被封闭在算法黑盒内，结果无法查询、解释与复盘
运筹优化求解过程中会产生大量关键的业务中间值（如每条产线在各时间桶的计划投料量、资源占用率、换产耗时等）。在外挂黑盒模式下，这些中间值只是算法内部的临时数学表达式，求解结束后服务只返回一个干巴巴的工单排程结果表（`output summary`）。当计划员质问“为什么加上共享投料口限制后，产线 B 的任务被推迟了两个小时”时，系统因为拿不到具名的中间值及其来源表达式，根本无法回答。

### 痛点 5：同一概念在系统与算法中重复编码，口径必然分叉
为了在前端页面展示预计消耗或做前置校验，后端程序员会在 Java/Kotlin 代码里写一套投料与产能公式；为了构建数学规划模型，算法工程师又会在算法服务里用符号变量重写一套同名逻辑。两套代码、两套单位换算、两套边界条件与异常处理，只要经历几次需求迭代，系统算出来的数与算法排出来的结果就会不可避免地发生漂移。

### 痛点 6：外部黑盒机器学习缺乏领域语义与版本治理，预测不敢进生产
当企业引入统计估算或机器学习模型预测设备产能、加工耗时或交期风险时，如果模型只是作为一个外部黑盒接口返回一个裸数字，系统就无法治理其背后的特征定义、观察窗口、标签截止时点、模型制品版本与质量指标。一旦把未经审批和边界校验的黑盒预测值直接当成排产输入，甚至混同于人工配置或实际产能事实，整个计划体系的可追溯性就会彻底崩塌。

### 痛点 7：求解结果退化为“成功/失败”字符串或原始日志，无法自解释
许多算法接口在返回求解状态时，只给出一个粗糙的布尔值（“有解/无解”）或直接把底层求解器的控制台日志抛给前端。这导致系统完全无法区分以下五种在业务决策上天差地别的情形：
1. **有解且已证明全局最优**（Optimal）；
2. **有解但因限时终止、尚未证明最优**（Feasible with Optimality Gap，若误标为“最优”会误导计划员）；
3. **经数学证明绝对不可行**（Proven Infeasible，此时需要定位究竟是哪几条约束发生了冲突，即最小不可行子系统 IIS）；
4. **问题无界或模型能力不支持**（Unbounded / Indeterminate）；
5. **仅因超时、取消或基础设施错误而未找到当前可行解**（No Incumbent，绝不能谎报为“业务方案不可行”）。

更进一步看，除了上述七大直接痛点，黑盒架构还堵死了通向智能化的另外四条关键路径：动态约束因缺乏结构化变量目录而无法在运行时安全注入；智能体因缺乏结构化领域上下文而无法落地推理；高频重复的客户现场规则因缺乏运行时画像（Profiling）与注册表而无法沉淀为正式能力；动态生成的规则因缺乏形式化类型与等价性验证而无法建立生产准入的可信边界。

## 1.4 两个相互咬合的根问题：领域知识由谁统一表达？新的领域能力如何进入系统？

穿透前面罗列的六大业务内耗、四重贫血 CRUD 困境与十一个黑盒算法痛点，我们会发现，阻碍企业软件进化的并不是某一个单点算法不够快，也不是某一个大模型参数量不够大，而是**两个相互依赖的架构根问题**：

1. **第一个根问题：领域知识由谁统一表达？**
   过去，BOM 展开、投料量、物料消耗、换产时间、生产时长、产能占用、资源使用量、替代料规则、排产约束等核心领域知识，被拆散在业务系统代码、运筹算法脚本、机器学习特征工程和智能体提示词中，导致业务语义与计算口径长期分叉。
2. **第二个根问题：新的领域能力如何进入系统？**
   过去，任何新的业务规则、流程差异和客户化长尾需求，都只能通过“需求分析 → 人工编码 → 测试 → 版本发布”的软件开发期链路进入系统。而在大语言模型时代，用户在真实运行过程中持续产生的业务意图与稳定使用模式，如何先由通用智能低成本承接，再经结构化、校验、仿真与专门化，安全沉淀为可复用的确定性软件能力？

这两个根问题的答案，共同构成了本书的核心架构蓝图：

```text
【根问题一：领域知识如何统一表达？】
                    │
                    ▼
            形式化领域模型
    （系统、运筹优化、机器学习、智能体的共同语义契约）
          │         │         │         │
          ▼         ▼         ▼         ▼
       数值解释   符号解释  统计/概率解释 语义解释


【根问题二：新的领域能力如何进入系统？】
                    │
                    ▼
       用户运行时意图 / 现场行为
                    │
                    ▼
      大语言模型 / 智能体语义前端
                    │
                    ▼
        语义中间表示（Semantic IR）
                    │
                    ▼
       类型/单位/权限校验 · 数字孪生仿真 · 语义编译
                    │
                    ▼
     确定性执行能力（查询计划 / 约束模型 / 流程计划）
                    │
                    ▼
   运行时画像采集 → 能力提升与专门化 → 失效回退与重新编译
                    │
                    ▼
   软件产品线工程（临时能力 → 客户专用 → 产品可变点 → 稳定核心）
```

如上图所示，这两个答案绝非孤立存在，而是互为前提：
* **用“形式化领域模型”回答第一个问题**：我们将领域知识从散落的代码和黑盒脚本中解放出来，建立一套可计算、带物理量纲、可版本化的形式化领域模型。系统侧对其进行**确定性数值解释**（负责纯函数计算、状态管理与事务治理）；运筹优化侧对其进行**符号解释**（负责变量映射、约束建模、优化求解与可行性认证）；机器学习侧对其进行**统计/概率解释**（负责特征构造、分布预测与受控参数校准）；智能体与大语言模型则对其进行**语义解释**（负责理解开放意图并生成结构化候选方案）。四者共享同一套业务概念定义，同时严格区分“需求量、计划量、预测量、预计量与实际执行事实”的状态角色，从根源上终结口径分裂。
* **用“大语言模型即运行时（LLM as Runtime）”回答第二个问题**：在统一的形式化领域语言之上，大语言模型不再试图越俎代庖去充当生产执行器或求解器，而是作为运行时的**语义前端**，将用户的开放意图压缩为受约束的语义中间表示（Semantic IR）。随后，语义编译器与自适应运行时接管接力棒，完成类型与权限校验、数字孪生仿真、降阶映射以及基于运行画像的热点专门化。

从传统软件工程的视角来看，从“解决语义分裂”到“实现运行时能力沉淀”，实际上是在补齐企业软件长期缺失的**六类根本工程缺口**，并将六个经典的软件工程方向整合成一条完整的生命周期闭环：

| 根本工程缺口 | 对应的软件工程方向 | 核心动作 | 在自适应软件体系中的核心职责 |
| :--- | :--- | :--- | :--- |
| **1. 语义缺口**：业务世界缺少统一权威定义 | **领域驱动设计（DDD）** | **定义世界** | 明确领域概念、限界上下文、聚合、业务不变量、状态角色与语义所有权，回答“这个业务世界到底是什么” |
| **2. 表达缺口**：业务知识无法被机器稳定组合与编译 | **领域特定语言（DSL）** | **描述世界** | 将领域语义转化为机器可读、可组合、可校验、可编译的业务语言（由形式化领域模型与 `ospf` 承载），回答“如何精确描述这个世界” |
| **3. 记忆缺口**：系统只有当前状态，缺少可追溯经验 | **事件溯源与审计** | **记住世界** | 保存领域事实、决策、人工计划调整、规则变化与能力演化的不可变时间序列，回答“这个世界是怎样走到今天的” |
| **4. 推演缺口**：知道当前状态，却不能安全试演未来 | **数字孪生（Digital Twin）** | **推演世界** | 建立包含计划/预计/实际三层时间的可计算、可仿真、可回放生产镜像，回答“如果这样做，接下来会发生什么” |
| **5. 生成缺口**：新的稳定需求仍完全依赖人工编码 | **产生式编程与语义编译** | **产生能力** | 根据经过校验的领域规范与语义中间表示，自动生成查询计划、数学约束、流程计划或受控制品，回答“如何把描述变成能力” |
| **6. 信任缺口**：动态产生的能力缺少安全准入边界 | **形式化方法与运行时验证** | **验证能力** | 以类型、物理量纲、不变量、契约、差分等价性、影子验证与运行时监测建立可信边界，回答“为什么这个新能力敢在生产环境执行” |

在这座由“定义 → 描述 → 记忆 → 推演 → 产生 → 验证 → 执行并产生新事件”构成的工程大厦中，大语言模型并不是与它们并列的“第七根支柱”，而是贯穿全链路的**语义前端、运行时推理器与能力编排器**。而在这一闭环之上，**软件产品线工程（SPLE）**则负责管理共性与可变性，把经过真实运行证据反复验证的动态能力，稳步提升为客户专用能力、正式产品可变点乃至平台稳定核心。

至此，我们的长期架构目标完成了一次决定性的跃迁：不再仅仅满足于“让人工智能帮助程序员更快地编写定制代码”，而是**让客户化与软件能力演进的一部分，从发布前的人工开发行为，转变为软件运行时的受控自适应行为**。

要真正理解这场范式革命为何必然发生，我们首先需要跳出具体的代码细节，回到软件工程演进的历史长河中，看一看从信息化、自动化到智能化，软件替人类承担的责任究竟发生了怎样的断代式迁移。这正是下一章我们将要展开的故事。
