# 目录与全书大纲（五卷 · 18 章 · 72 节）

## 第一卷：范式革命篇 —— 从 Software 1.0 到 LLM as Runtime
* **第 1 章：被“增删改查”与“外挂黑盒”困住的企业软件**
  * 1.1 一场横跨 ERP、APS、MES、WMS、TMS 的急单风暴：为什么系统越建越多，现场排产却越来越累？
  * 1.2 传统贫血 CRUD 架构的局限：散落在应用服务、数据库脚本、报表与人工经验里的业务口径
  * 1.3 “外挂黑盒算法服务”的七大工程痛点：拼装数据成本高、无状态难感知与中间值不可解释
  * 1.4 两个相互咬合的根问题：领域知识由谁统一表达？新的领域能力如何进入系统？
* **第 2 章：从信息化到意图驱动 —— 软件替人类承担了多少认知责任？**
  * 2.1 软件演进的四个阶段：信息化（记录）、自动化（按规则做事）、前 LLM 智能化（特定判断）与 LLM 智能化（理解目标）
  * 2.2 真正的历史断点：软件能力形成的位置，从“发布之前”延伸到了“使用之中”
  * 2.3 传统项目制交付的死结：为什么靠“提需求—写代码—测接口—发版本”永远追不上长尾变化？
  * 2.4 重新定义人与软件的关系：过去用户只是使用程序，未来用户在使用程序的同时也在持续塑造程序
* **第 3 章：重读 Software 1.0、2.0 与 3.0 —— 两条正交的软件进化轴**
  * 3.1 Andrej Karpathy 的三代软件范式：代码定义行为（1.0）、数据塑造行为（2.0）与意图驱动行为（3.0）
  * 3.2 为什么三代软件不是淘汰关系，而是能力形成方式的层层叠加？
  * 3.3 两条正交的演进轴：软件能力形成方式（1.0 → 2.0 → 3.0）vs. 四类计算范式（确定性、运筹优化、机器学习、语义推理）
  * 3.4 核心洞察：前大模型时代的传统算法与软件不会被淘汰，而会成为大语言模型的“编译目标”
* **第 4 章：核心命题：LLM as Runtime（大语言模型即运行时）**
  * 4.1 为什么“把开发工具搬进聊天框、让大模型直接在线写生产代码”在工业界是死路一条？
  * 4.2 什么是真正的 LLM as Runtime？将大语言模型定位为运行时的“业务语义前端”
  * 4.3 为什么它更像“即时编译（JIT）”，而不是“任意代码生成”？
  * 4.4 生产执行铁律：自然语言永远停留在候选层，确定性机制负责把守生产执行边界

## 第二卷：语义底座篇 —— 形式化领域模型与 OSPF 运筹建模框架
* **第 5 章：三原生统一于形式化领域模型 —— 终结业务语义分裂**
  * 5.1 为什么说“各运行侧共享同一形式化领域模型”是整座架构大厦的根基？
  * 5.2 同一业务概念的四种正交解释：系统侧数值解释、运筹侧符号解释、机器学习侧统计解释与智能体侧语义解释
  * 5.3 状态角色隔离：为什么统一“投料量”定义，绝不等于把需求量、计划量、预测量、预计量和实际量混为一个字段？
  * 5.4 形式化领域模型的八大最低构成要素与运行时实例边界
* **第 6 章：初识 OSPF —— 面向软件工程师的代数化数值与量纲安全底座**
  * 6.1 为什么在工业软件里直接用裸 `Double` 浮点数写公式是一颗定时炸弹？
  * 6.2 代数化数值类型层次（`RealNumber`）：整数、有理数、浮点数与任意精度数的泛型抽象及精度容差治理
  * 6.3 物理量纲与单位安全（`Quantity` / `PhysicalUnit`）：让“重量加时间”或单位错配在校验期直接显式失败
  * 6.4 线性换算与仿射转换：跨系统（ERP/APS/MES/WMS）单位口径的统一收敛
* **第 7 章：一鱼两吃 —— 统一表达式中间表示（Expression IR）与同源双入口**
  * 7.1 传统研发的分裂之痛：后端程序员用业务代码算物料消耗，算法工程师用脚本重写一遍投料约束
  * 7.2 OSPF 表达式中间表示（Expression IR）：常量、稳定符号身份、属性路径与不可变语法树
  * 7.3 共享业务核心的双入口架构：系统侧代入具体数值直接求值 vs. 运筹侧代入符号变量生成约束片段
  * 7.4 部分求值、编译求值缓存与等价性性质测试：用自动化测试证明系统计算与算法模型 100% 口径一致
* **第 8 章：像搭积木一样表达复杂业务 —— 结构化函数、逻辑算子与求解器解耦**
  * 8.1 化非线性为线性：绝对值、松弛变量、分段线性与阶梯规则的规范化与代数分类
  * 8.2 把业务分支装进数学模型：布尔逻辑、条件分支、选一约束与多目标软约束权衡
  * 8.3 类编译器降阶架构：如何让领域模型彻底摆脱对特定商业或开源求解器 API 的绑定？
  * 8.4 显式错误契约（`Result` / `Ret`）与能力检查：严禁静默截断高阶项，当求解器能力不支持时如何优雅报错或降级

## 第三卷：工程支柱与世界模型篇 —— 记住过去、推演未来与白盒诊断
* **第 9 章：自适应软件的六大工程支柱 —— 跨越半个世纪的软件工程合龙**
  * 9.1 六大根本缺口：语义缺口、表达缺口、记忆缺口、推演缺口、生成缺口与信任缺口
  * 9.2 六个软件工程方向的分工：领域驱动设计（定义）、领域语言（描述）、事件溯源（记忆）、数字孪生（推演）、产生式编程（产生）、形式化方法（验证）
  * 9.3 从“定义 → 描述 → 记忆 → 推演 → 产生 → 验证 → 执行”的完整演进闭环
  * 9.4 大语言模型在闭环中的真实坐标：不是第七根支柱，而是贯穿全链路的语义前端与编排器
* **第 10 章：运行时的世界模型 —— 事件溯源（过去）与可计算的数字孪生（未来）**
  * 10.1 为什么只有“当前状态”的系统既无法复盘追责，也无法支撑机器学习与能力沉淀？
  * 10.2 事件溯源与版本快照：保留事实、决策、人工调整原因与规则版本的不可变时间轴
  * 10.3 告别“静态展示看板”：基于计划时间、预计时间、实际时间三层模型的数字孪生动态推演
  * 10.4 换产时间、生产时长与日历可用性的领域沉淀：如何实现“前序任务延误 → 后序预计状态秒级自动更新”？
* **第 11 章：用领域驱动设计（DDD）白盒编排运筹算法与大规模分解求解**
  * 11.1 15 点架构依赖推演：为什么算法必须优先作为可被应用层白盒编排的库与模块？
  * 11.2 局部推演 vs. 全局滚动排产：如何划定局部时间传播与触发完整重排的策略边界？
  * 11.3 用 DDD 架构驾驭列生成（Column Generation）：受限主问题、定价子问题契约与约化成本验证
  * 11.4 用 DDD 架构驾驭 Benders 分解：主子问题解耦、可行割/最优割验证与收敛认证边界
* **第 12 章：告别“无解报错” —— 正交求解结果协议（SolveReport）与分层自解释**
  * 12.1 为什么只返回“成功/失败”或一段求解器日志会让计划员寸步难行？
  * 12.2 正交求解结果协议（`SolveReport`）：解耦问题状态、终止原因与解存在性，严禁把“超时未得解”谎报为“不可行”
  * 12.3 有解与无解的数学证据：最优差距（Gap）、松弛量/违反量、关键紧绑定约束与最小不可行子系统（IIS/冲突集合）
  * 12.4 求解结果自解释的四层架构：从底层数学证据、算法符号映射、业务对象绑定到智能体本地化归纳

## 第四卷：三原生协同与意图转化篇 —— 当大语言模型、机器学习遇上运筹优化
* **第 13 章：三原生交响曲 —— 运筹优化（OR）与机器学习（ML）的三大双向增强**
  * 13.1 机器学习原生（ML-Native）：冻结特征模式与数据版本，让产能与耗时预测携带质量指标、不确定性与血缘进入审批流
  * 13.2 增强机制一（ML 辅助 OR）：从单点预测走向鲁棒优化、随机规划、机会约束、CVaR 与分布鲁棒优化（DRO）
  * 13.3 增强机制二（OR 约束下的 ML/RL）：用受约束强化学习加速列生成定价与 Benders 子问题，由运筹主问题守住可行性与精确兜底
  * 13.4 增强机制三（决策反馈驱动的参数校准）：从计划员的人工调整差异与原因码中学习目标权重与软约束偏好
* **第 14 章：智能体原生与业务语义前端 —— 从模糊自然语言到语义中间表示（Semantic IR）**
  * 14.1 给智能体装上“业务词典与语法”：暴露结构化领域元数据、可引用变量、中间值、约束模板与流程契约
  * 14.2 结构化推理上下文裁剪：结合当前数字孪生状态、历史快照与异常事件进行影响范围推理
  * 14.3 语义中间表示（Semantic IR）：查询中间表示、约束中间表示与流程中间表示的设计规范
  * 14.4 动态约束转化实战：从“今天 A、B 线共用投料口，总投料不超 1000 公斤”到可哈希、可编译的结构化线性约束候选
* **第 15 章：可信执行边界 —— 从候选语义到生产执行的八步管线与防幻觉护栏**
  * 15.1 从对话到沉淀能力的八步标准流水线：采集 → 规范化 → 中间表示 → 验证 → 优化 → 降阶映射 → 发布 → 自适应监控
  * 15.2 形式化方法作为横切可信基础：类型、量纲、租户权限、预算配额、前置/后置契约与业务不变量检查
  * 15.3 在进入生产前证明自己：数字孪生沙盒仿真、通用/专用路径等价性验证与影子运行
  * 15.4 运行时八大核心风险治理：防御语义漂移、权限穿透、错误固化、环境变化、代码供应链风险、过度专门化、事件历史失真与仿真失配

## 第五卷：运行时进化与全景实战篇 —— 从动态探索到自适应 DOP 平台
* **第 16 章：语义即时编译（Semantic JIT）—— 运行画像驱动的热点专门化与失效重建**
  * 16.1 动态查询即时编译与动态约束专门化：用“规范化语义形状”聚合同类请求，而非按原始文本统计
  * 16.2 运行时画像（Profiling）与晋升阈值：综合调用频率、延迟、扫描行数、计算成本与业务收益决定是否专门化
  * 16.3 三层专门化阶梯（Tier 0 → Tier 1 → Tier 2）：从通用规划器、参数化计划/预编译约束，到受控虚拟机插件的按需升级
  * 16.4 计划注册表与去优化：当数据库结构、字段目录或权限策略变更时，如何精确标记失效并自动回退通用路径？
* **第 17 章：驯服复杂性 ——《人月神话》、软件产品线工程（SPLE）与四级能力晋升**
  * 17.1 重温《人月神话》：当大模型让“生成新能力”的边际成本暴跌，如何守住系统的“概念完整性”？
  * 17.2 为什么运行时动态化不是终点，而是发现未来稳定产品结构的探测机制？
  * 17.3 软件产品线工程（SPLE）的四级能力晋升漏斗：临时能力 → 客户专用能力 → 产品可变点 → 平台稳定核心
  * 17.4 五大核心平台资产沉淀：语义中间表示、语义编译器、能力注册表、自适应运行时与产品线可变性模型
* **第 18 章：全景实战与演进蓝图 —— 从零构建自适应数字化运营平台（Adaptive DOP）**
  * 18.1 贯穿用例全景复盘：数据驱动产能估算审批 + 产线 A/B 共享投料口受限 + 前序任务 T1 延误 + 跨系统协同重排
  * 18.2 工程落地六阶段路线图：统一领域模型 → 运筹原生化 → 事件溯源与数字孪生 → 机器学习原生化 → 智能体语义前端 → 运行时专门化与产品线晋升
  * 18.3 软件研发范式的全面重构：需求、开发、测试、发布、架构与产品工程的七大转变
  * 18.4 未来工程师与组织画像：从“写 CRUD 与调提示词的人”进化为“智能系统与语义编译器工程师”
